# Semrush / Similarweb 平台能力测绘

**这份文件回答一个问题：这两个付费面板到底能拿到什么，拿不到什么。**

机器可读的同一份事实在 [`../data/provider-capabilities.json`](../data/provider-capabilities.json)，
用 `node scripts/rankup-cli.mjs catalog <provider>` 读。**这份 Markdown 是给人看的判断依据，
JSON 是给脚本用的数据。改了一边必须改另一边**——`provider-cli.test.mjs` 会校验 JSON 结构，
但没有任何东西能校验这两份文件是否一致，只能靠改的人自觉。

来源：2026-08-27 用 OpenCLI 驱动真实登录态点出来的，不是抄官方文档。

**修订本文件之前**：用的时候发现和这里写的对不上，先按 [`discipline.md`](discipline.md) 十五的五层分诊走一遍（重跑、浏览器与会话、额度与配额、人眼截图对照、跨时段复现）。五层全过才是面板真的变了，才改这里并同步 JSON；否则只记项目侧 `journal/`。一次环境故障被写成「这个报表没了」，比不回流更糟。
边界见本文最后一节「没摸到的地方」——**那一节比前面所有内容都重要**。

## 先说验证强度：枚举数 ≠ 验证数

**这份文件里的页面数是「侧栏枚举到的名字数」，不是「取到过数据的页面数」。**
两者差得很远，写在这里是因为它们曾经被混着读：

| | 枚举到的页面 | 真正取到过数据 | 比例 |
|---|---|---|---|
| Semrush 工具箱 | 102 | **16** | 16% |
| Semrush 应用中心 | 16 | — | 不适用 |
| Semrush 合计 | 118 | **16** | |
| Similarweb | 73 条路由 | **30** | 41% |

**应用中心那 16 页单独列，是因为把它们并进分母会让这张表更不准，不是更准。**
它们是 `/apps/` 首页加 15 个分类**列表页**——列表页本来就没有「报表数据」可取，
永远不可能进「取到过数据」那一列。混进去只会稀释比例（16% 会被摊成 14%），
制造一种「覆盖率下降了」的假象，而实际上是我们多枚举了一批本质不同的页面。
这 16 页是 `enumerated`：只读到卡片上的名字、描述、价格和 Active 标记，一个 App 都没打开过。

**工具箱那 102 页**里，除去已取数的 16 页：11 页摸到边界但没数据、4 页权限拦、
**49 页属于「做」这一层，按红线直接没执行**。所以 16% 不代表工作没做完，但它确实代表
**「102 个页面的能力图」的准确说法是「102 个页面的名字 + 16 个页面的事实」**。

引用本文任何一条能力时，先去 JSON 里看那一项有没有 `observed` —— 没有的就是名字。

> **Similarweb 那 73 条路由要打一个折**：2026-08-28 发现面板对未知路由会**静默重定向**，
> 而那一轮的探测**没有记录落地 hash**。所以「73 条路由」里有多少是深链到达、
> 又恰好被重定向到了同一个有内容的页面，现在无法回答。
> 详见第三节「未知路由静默重定向」，逐条审计在 JSON 的 `liveAudit.evidenceAudit`。

## 零、先记住这一句

| 平台 | 一句话 | 什么时候用它 |
|---|---|---|
| **Semrush** | **工具箱 + 施工队**：既侦察别人，也能动手改你自己的东西 | 关键词、谷歌排名、外链、竞品广告；要"分国家"精确到词的量 |
| **Similarweb** | **望远镜 + 卫星图**：基本只能看不能动，但看得远 | 流量大盘、行业格局、渠道构成；要"这个站到底多大" |

**选错的典型后果**：拿 Similarweb 去查"某个词在美国多少量"——它给的是网站级、行业级的数，
不是关键词级的精确量；拿 Semrush 去问"这个站一个月多少人"——它给的是**模型外推的自然流量**，
只覆盖它追踪到的词，小站会严重低估。两者口径差异的完整裁定见
[`experiences/webcafe-experiences.md`](experiences/webcafe-experiences.md) 十六·五。

## 〇·五、跨平台哪些数能并列，哪些不能

【实测 2026-08-28，`canva.com`】以前本仓库三处脚本注释都写着「Semrush 的流量与
Similarweb 不同口径，不要并列」。那句话**对的是自然搜索口径**，但它读起来像
「Semrush 没有可比的数」——而 Semrush 的 Traffic & Market（.Trends）给的就是总访问量，
和 Similarweb 同一个问题。这条线此前一直没摸到，所以从没比过。

| 指标 | Semrush .Trends（2026年7月，全球） | Similarweb | 差异 | 能不能并列 |
|---|---|---|---|---|
| **总访问量** | 7.9亿 | 771.4M | **+2.4%** | ✅ **能** |
| 桌面占比 | 84.26% | 82.56% | +1.7pp | ✅ 能 |
| 移动占比 | 15.74% | 17.44% | −1.7pp | ✅ 能 |
| 跳出率 | 30.23% | 26.99% | +3.2pp | ⚠️ 大致可比 |
| 页数/访问 | 5.4 | 6.39 | −15% | ⚠️ 只能比大小 |
| **平均访问时长** | 11:02 | 05:56 | **+86%** | ❌ **不能** |

**两条可以直接用的结论**：

1. **总访问量可以互相校验。** 两家用完全不同的面板和模型，落在 2.4% 以内。
   拿其中一家的数当另一家的合理性检查是成立的——差到数量级就是有一边错了。
2. **参与度类指标不能并列，尤其是访问时长。** 差了近一倍。要么两家的「一次访问」
   定义不同，要么会话超时阈值不同。**不知道原因之前，不要把两家的时长放进同一张表。**

⚠️ 口径限度（必须一起转述）：Semrush 那侧是 2026 年 7 月整月；Similarweb 的总访问量
标的是 `Jul 2026 - Aug 2026`，参与度指标标的是 `Last 28 days (As of Aug 24)`。
**窗口不完全重合**，能解释一部分差异，但解释不了访问时长那近一倍的差距。

对应的取数入口：Semrush 侧 `/analytics/traffic/traffic-overview/`（当前没有脚本，
见下一节）；Similarweb 侧 `similarweb-query.mjs --domain <域名>`。

### 这条工具线上，空表不等于没数据

**结论没变，例证换了。** 本节此前拿「节点 5 得 0 行、节点 8 得 850 格」当例证，
**那个节点差异不存在**，见下面的更正。规则本身现在证据更强：同一个节点上，
同一条路由同一个月份，一次 0 行、一次满表。

> 针对本模块写取数脚本时，**必须把「读到 0 行」和「这个域名没有数据」分开报**，
> 并且在报空之前重读一次，同时记下读取瞬间的 `document.visibilityState`。
> 把 0 行当成业务结论，就是本仓库反复出事的那一类错误。

⚠️ **但「空」有两种，别合并**：可见性伪空（`visible` 一读就满）和 A 类
「本来就没表」（`visible` 连读 3 次仍 0 个表格元素，只有图）。判据和实测见
下面「两种『空』是并存的两回事」一节；这条规则的重读补救只对前者有用。
**⚠️ 2026-08-28 更新：曾经的第三种「静默空表」已经整类清零**——8 条全部是等得不够，
详见下面「`empty-silent` 这一类已经归零」；而 A 类那 10 条也在重测中，尚未确认。

⚠️ **写就绪判据之前，先读 backlink Skill 里 id 为 `readiness-must-bind-to-this-query`
的那条 law。** 2026-08-28 一天之内，同一类错误在这条工具线上出现了**六次**：判据检查的是
「页面上有没有某个东西」，而那个东西可以由**与本次查询无关的来源**提供（营销文案、装饰 svg、
邻居工具的挂件、保存列表里的历史记录），第五种更隐蔽——把「连续 N 次读到空」当成「确认是空」，
**第六种是第五种的补丁本身**：给它加一个「最小等待下限」，形状没变，只是把赌注换了个数字。
**六个实例、成因和正确判据形状只写在那条 law 里，本文件不复述，只指路。**

#### 更正 2026-08-28：可见性不是这一侧能控制的量

同一批实测还推翻了「按某个配方就能买到可见性」的说法。同一个会话、期间什么都没做：

| 时刻 | `visibilityState` |
|---|---|
| 全新 `window: 'foreground'` launch 落地那一刻 | `visible` |
| **一次页内 `location.href` 导航之后** | `hidden` |
| 再隔约 10 分钟、未做任何操作 | 又变回 `visible` |

推测机制：Chrome 对**被其它窗口遮挡**的窗口报 `hidden`，取决于机主桌面此刻
哪个窗口在前——CLI 这一侧管不了。**所以正确策略不是「设法让它可见」，
而是「只采信可见时的那一次读」**。协议现为**耐心模式**：每条路由 3 轮导航、
每轮 200 秒跑满不早停、单条最长 600 秒；`filled > 0` 判 `data`；
判「空」除了连续 3 次在 `vis === 'visible'` 下读到空，**还必须拿到一个正向的
「本页已渲染完成」信号**（分页器 / 行数计数 / 加载指示消失）——**等待时长不是那个信号**；
拿不到信号就判 `inconclusive`，全程没等到过 `visible` 就判 `inconclusive-hidden`，
**两种都绝不记成「空」**；每次读都记 `visibilityState`。
（此前那版「连续 3 次可见读且等满 100 秒」的判据**已被同日重测推翻**，见下面的分布一节。）详见 backlink Skill 里
id 为 `hidden-tabs-do-not-hydrate` 的那条 law。

#### AI 流量：两次独立跑数值完全一致，可采信

`/analytics/traffic/ai-traffic/` 的 **120 格**在两次**独立**的跑里逐字相同
（一次 background、一次 v4-visible）：`chatgpt.com / 无类别 / 64.62% / 363.9万`。
两次独立复现是本模块目前最强的可采信证据，这条不必再复测。

#### 同批的两条方法学发现

- **已经水合之后切到后台，数据还在。** `visibilityState=hidden` 时仍然读到 850 个非空单元格。
  所以可见性门控的是**首次水合**，不是后续读取。
  ⚠️ **但反过来不成立：不是所有的空都是水合问题。** 同一批实测里另有 10 条 `chart-only`
  路由，`visible` 下连读 3 次仍然 **0 个表格元素**，只有 svg——看上去不是水合截面，
  页面本身就不提供表格，套可见性重试循环是白费。**这 10 条的原判定来自早停判据，
  2026-08-29 重测后已拆成四档，只有 4 条通过结构判据可采信，另有 4 条退回 `pending`——
  见下面「`chart-only` 那 10 条：拆成四档」。** 判断一条空属于哪一类之前，
  先读 backlink Skill 里 id 为 `readiness-must-bind-to-this-query` 的那条 law：
  「读到空」本身就是一个需要判据的结论，而不是一个观测事实。
- **`windowMode` 和 `visibilityState` 对不上。** 脚本传给 opencli 的模式名只是意图：
  标记 background 的那次读到 `visible`，标记 foreground 的那次读到 `hidden`。
  **唯一可信的记录是读取瞬间在页面里读到的 `document.visibilityState`。**
  任何按「当时是前台还是后台」归因的旧结论都要按这条重做。

另外两条同批实测：

- **国家页在节点 5 和节点 8 上都是空的**（`流量比例 n/a`、`访问量 n/a`）。这和主要页面
  是**两种不同的失败**，不要混为一谈。
- URL 上的 `lid=` 是**按账号隔离的列表 ID**。拿一个节点的 lid 去另一个节点，
  页面会静默落回空态落地页——而页头此时不显示目标域名，这是唯一的区分线索。
  ⚠️ **归属更正 + 待复测（2026-08-28）**：这条一度被当成 **Similarweb** 侧的结论派出去复测，
  **它不是 Similarweb 的**。查证结果：`lid` 在 JSON 里只出现一次，就在
  `providers.semrush.savedListCheck`，证据用的是 Semrush 的 node 5 / node 8；
  `providers.similarweb` 下没有任何 `lid` 记录。**这条留在 Semrush 名下，状态 `pending-remeasure`。**
  **而且它比原先判断的更值得复测**：它的判据是「拿别的账号的 lid 会**静默落回空态**」——
  也就是**读到空 ⇒ 下结论**，正是这一天被反复证伪的那种形状；而本节开头写的就是
  「这条工具线上，空表不等于没数据」。在复测回来之前，**不要用这条去解释任何一次空读**，
  也不要据此断定跨账号 lid 一定不可用。复测要求见 JSON 的 `savedListCheckLidRemeasure`。


### 流量与市场 22 条路由的实测分布（node 5，canva.com，2026-08-28；2026-08-29 按 B 的最终报告更新）

**先说能拿走的那一句：想要表格数据，这条线上有 11 条路由能给，而不是 3 条。**
早先写的「只有 3 条」是**早停判据的产物**，不是这个平台的性质——见下面「`empty-silent`
这一类已经归零」。**2026-08-29 B 的最终报告回来之后，`pending` 已经清零**，这个 11 不再是下界，
是当前的确定值。

**先把口径钉死，因为 11 和下表的 `data: 10` 差一条。** 差的是 `top-pages`（850 格），
它**不在 node 5 这次 sweep 的 22 条里**（另一次实测，见上面「节点差异是观测假象」一节）。
所以：**22 条之内 `data` 10 条；把 `top-pages` 算进来，能直接喂给取数脚本的共 11 条。**

##### 为什么会错两次 —— 而且第二次是第一次的「修复」

**第一次（判据 v4）**：「`vis === 'visible'` 且累计 3 次可见读 → 采信为空」，
可见读间隔 6 秒，**最快 18 秒就下了「空」的结论**。而这些页面的渲染顺序是
**摘要 → 图表 → 表格，表格永远最后**——表格还没开始渲染的时候，连续读多少次都是
**稳定的空**。**「稳定」不等于「完成」。**

> **这条实测机制值得单独记住**：**摘要区已经出数、表格仍 0 行，是正常中间态，不是空表。**
> 而 `captureStable` 那套「读两次一致就收下」在这里**恰好会被稳定的空态骗过**——
> 0 行本身就是完全稳定的，两次一致来得又快又毫无意义。

**第二次（判据 v5，也就是第一次的修复）**：给它加一个「最小等待下限」——
「可见读满 3 次 **且** 本轮等满 100 秒」，每轮上限 150 秒。**这个下限同样不够。**
上表 8 条里，`geographical-regions` 和 `business-regions` 是**第二次重测**才出的数——
100 秒没兜住它们，而且**同一页两次表现不一样**。重表格页的水合时间跨度大而且不稳定。

##### 正确的方向不是把下限调大

**固定时间下限本身也不是充分条件。** 100 秒被证明不够，600 秒是现在的经验值而不是保证。
**只要判据的形状是「等够久 + 还是空 → 判空」，它就永远只是在赌一个阈值**，
而阈值随页面、随目标、随负载变化。所以规矩改成：

- **「空」这个结论默认就是暂定的**，不是等够时间就能转正的；
- **判空必须绑定到一个正向的「本页已渲染完成」信号**——分页器出现、行数计数出现、
  加载指示消失、某个只在数据到位后才出现的控件。这种信号和「非空单元格」一样，
  是**本次查询的产物**；等待时长不是；
- **拿不到那种信号时，输出 `inconclusive` 而不是 `empty`。** 这两个词对下游的意义完全不同，
  本仓库的规矩是宁可显式失败；
- **时间下限保留，但它是兜底不是判据**：它约束一轮能跑多久，不构成下结论的理由。

现行协议 **`v6-patient-signal-gated`**：每轮 200 秒、3 轮跑满不早停、单条最长 600 秒。

**被推翻的记录一律保留，标注在 JSON 的 `supersededObservation` 里，不删。**
正是因为旧记录还在，才比得出「摘要有数、表格 0 行」这个关键对照。

这两次分别是那条 law 的**实例 5 和实例 6**。另外：仓库里 `captureStable` 的注释早就写过同一件事
（这些厂商的指标区分两拍渲染，只认标签的就绪判据会在中间态通过，错得很安静），
**这次等于又犯了一遍**——教训当时被记成了「关于 `captureStable` 的事实」，
而不是「关于判据的事实」，所以没有迁移过来。

#### `chart-only` 那 10 条：拆成四档，只有一档可采信（2026-08-29）

> ⛔ **本小节整节的结论已于同日晚些时候作废**，见本节开头的作废公告：
> 下面的 `chartHydrated` / `exportBtns` 计数出自一个对 shadow DOM 失明的探针，
> 两个信号已退役，9 条 `structural-confirmed` 全部回到 `pending-remeasure`。
> **原文保留，只标注被什么推翻。**

它们原本是**同一个早停判据下测出来的**，同一个 bug。表现确实和「静默空表」不同——
**连 `table` 元素都不存在**，而不是有表 0 行——但这不构成免测的理由，原话：
**「虽然它们的表现不同，但我不能凭这个就免测。」** 耐心模式重跑之后结果如下。

**判据不在这里。** 区分「这条路由本来就没有表格」和「表格还在路上」，
用的是一条四条件、连续两次读都要满足的**结构判据**，以及两个刻意分开的判定名
`no-table-structural`（可采信）/ `no-table`（不可采信），2026-08-29 又加了第三个
`data-not-in-table`。**判据全文和三个判定名只写在**
backlink Skill 里 id 为 `readiness-must-bind-to-this-query` 的那条 law 的 `<correct>` 块里，
这里不复述，也不要在别处再抄一份。只记住它的含义一句话：
**「页面别的部分都好了，就是没有表格这个东西」**——光是「没有 table 元素」证明不了任何事，
因为还没开始渲染的页面同样没有 table 元素。

**2026-08-29 判据修订：结构判据去掉了 `vis === 'visible'` 那一项，保留「目标已生效」那半。**
去掉的理由两条，互相独立：

1. **没必要。** `chartHydrated` 和 `exportBtns` 已经**直接**证明「页面其余部分渲染完了」，
   而且这些页面的渲染顺序是 摘要 → 图表 → 表格，**图表数字渲染出来 = 流水线已经走到表格的前一站**。
   可见性只是同一件事的代理项，效果本身可观测时，代理项不增加任何信息。
2. **有害。** 一次 foreground attach 会把 `visibilityState` **永久锁死在 `visible`**
   （铁证：同一个 Chrome 窗口里两个标签页同时报 `visible`）。于是这个条件
   **在被污染的会话上恒真**（形同虚设），**在诚实的纯后台会话上反而可能为假**（误杀一条成立的结构判定）。
   一个「在它恒真的地方不增加信息、在它诚实的地方偶尔为假」的条件，比没有还差。
   ⚠️ **措辞收窄 2026-08-29（Experiment F）**：被钉住的会话不是在「撒谎」——
   rAF 帧数证明它**真的按 visible 调度**（181 帧）。它只是把 `visibilityState`
   变成了一个恒定值，因此**不再是一次测量**。去掉这一项的结论不变，理由更准确了。

**保留「目标已生效」那半是必须的**：空态落地页是一个**完美的 `noTable === true`**。
条件一被满足得最彻底的那个页面，恰恰是根本不是你那份报表的页面。

**连带结论：4 条 `structural-confirmed` 的判定不受 `visible` 锁死污染影响**，
因为它们靠的是图表数字和导出按钮，都是页面产出。
`referral` / `organic-search` 那 98 / 96 次「visible 读」**作为可见性证据不成立**
（`semrush-traffic.mjs` 的 `DEFAULT_WINDOW = 'foreground'`，那个字段在这些会话上是恒定值），
但它们从来不是可见性证据——是 98 / 96 次「0 个 table 元素」的 DOM 观测，这一点不受影响。
**所以那批读数的可信度既不提升也不下降。**
⚠️ **收窄 2026-08-29（Experiment F）**：这里说的「作废」只是**作废它作为可见性证据的身份**，
不是作废读数。这些标签页建时就是 foreground，**它们确实是 visible 的**，
DOM 观测本身有效。**不要因为这条去重跑它们。**

⚠️ **这不动摇「可见性伪空」那条 law。** 两者说的是两件事：
可见性管的是**表格里的行会不会水合**（`top-pages`：hidden 0 格 / visible 850 格，三次交叉验证），
不是**`table` 这个元素存不存在**。结构问题和取值问题，别合并。

**`behavior` 从「弱证据 pending」翻案成一个独立类别，方向和原来相反。**
原来记的是 `chart=0 / exp=0`，读作「整页章节都没渲染，等于什么都没测到」。
实测复查发现它**根本没有 table 元素，而数据一直在页面上**，用列表 + 条形图呈现：

> `YouTube 71.8% 1.5亿 | Facebook 49.36% 1亿 | Instagram 48.61% | Reddit 33.71% | TikTok 28.06%`

另有兴趣度和设备分布。**按「非空单元格 > 0」判，它得 0——而正确结论绝不是「没数据」。**
那次 `chart=0 / exp=0` 的读数本身没错，错的是拿它去回答「这条路由有没有数据」；
它只能回答「有没有**表格型**数据」。

取数方式：**按路由声明 `presentationShape` 和本路由自己的锚点维度名**
（`behavior` 是 社交媒体 / 兴趣度 / 设备），在锚点标题所属的 section 子树里取数值。
⚠️ **绝不能改成「页面上有数字就算有数据」**——那正是 `axa.fr` 挂件那个假阳性。

⚠️ **`chart-only` 和 `empty-silent` 的补救方式相反**（前者重读没用、后者要等），
这个区分本身仍然成立；`empty-silent` 已清零，`chart-only` 9 条全部结案。
**`data-not-in-table` 是第三种，两种补救都不适用**：重读没用，等也没用，要换读取形状。

## 一、把功能分成三层：看 / 追 / 做

所有 SEO 工具的功能逃不出这三种。**判断该买谁、该用哪个，先看它在哪一层。**

| 层 | 是什么 | Semrush | Similarweb |
|---|---|---|---|
| **看** | 输一个域名/关键词，出一份一次性报告 | 强 | **最强** |
| **追** | 设好之后每天自动跑，变差了告诉你 | **很强** | 弱（只有 Rank Tracker + Site Audit） |
| **做** | 真动手改东西：写文章、发帖、管商家资料 | **很强** | 几乎没有 |

**对本项目的直接含义**：

- 「做」这一层我们**一次都不会用**——本项目所有脚本都是只读取数，
  而且安全约束明令禁止执行写操作（见下方「红线」）。Semrush 已知有 **49 个页面属于这一层**，
  接近总数的一半是无效面积。规划取数脚本时不要把它们算进覆盖率分母。
- 「追」这一层目前**没有任何脚本覆盖**。这是最大的能力空白：
  竞品监控、排名跟踪、网站体检都得靠人记得去看。
- 「看」这一层是脚本战场，现有脚本全部落在这里。

### 页面卡在「一直加载」时：主动刷新，不要下结论

面板偶尔会卡住不渲染（正文空白、骨架屏、spinner 不停）。**这是偶发故障，不是页面没有内容。**

```bash
opencli browser <session> open "<同一个 url>"      # 或 eval 里 location.reload()
# 别用 `wait time` —— opencli 1.8.7 里它不到一秒就返回，等于没等（实测见下）
opencli browser <session> eval '(async()=>{await new Promise(r=>setTimeout(r,5000));return true})()'
```

> **`wait time N` 是坏的，这条会直接害你误判。** opencli 1.8.7 实测：`wait time 1`、`5`、`12`
> 全部约 0.97 秒返回，`--timeout` 调大无效。**"等 20 秒还没渲染出来" 很可能根本没等够 1 秒。**
> 本轮审计里那些「表格 25–40 秒仍不渲染」的失败，有多少是这个原因造成的，现在无法回溯确认。
> 有条件可等时优先 `wait selector` / `wait text`（这两个是好的）；只能硬睡就用上面那行 eval。
> 详见 `opencli` Skill 的 `references/browser-driving.md`。

- 刷新 **2–3 次**仍然卡住，才记 `unavailable`，并写明「刷新 N 次后仍卡加载」。
- **绝对不要把「卡加载」写成「该功能不存在」或「零流量」。**
  这是本文件最容易犯也最贵的错——把偶发故障固化成能力目录里的假结论，后面所有人都会照着它做决策。
- 派浏览器 sub-agent 时**必须把这条写进 prompt**，否则它会干等到超时然后报失败。

### 表格空了，先看是不是「已达到每日报告限额」，不要先怀疑这个域名

Tools Share 面板是共享账号代理，**下拉里每一个节点都是一个不同的账号**。2026-08-27 实测：
默认节点跑 Semrush 报表返回「已达到每日报告限额」，换到另一个当天还没用满的节点后同一份
报表立刻跑通——这是账号级的每日配额用尽，不是这个域名/关键词本身没有数据。

**这条之所以危险**：一张被限额的页面**照样渲染完整的表头**，所有列名都在，只有表体被换成
了那句限额提示。任何只认表头出现就判定「就绪」的检查会直接通过，然后把这张空表当成
「这个域名没有数据」写进结论——**限额被读成"没有数据"，是一个看起来完全正确、实际彻底
错误的答案**，比一次显式报错贵得多。

**目前没有任何脚本会自动帮你挡住这一页**——backlink 的 `semrush-report.mjs` 有一段试图识别
这句提示的正则（`QUOTA_BLOCKED`），但据复核，它当前是死代码，还没能在真实限额页面上生效；
其余取数脚本完全没做这项检测。所以判据只能靠人（或调用脚本的 agent）自己执行：**读表前
先在表体文字里找一遍「已达到每日报告限额」**；命中就是节点问题，换节点重跑，不是这个
域名/关键词真的没有数据。不要假设这一步已经被自动化替你做了。恢复命令：

```bash
node backlink/scripts/tools-share-node.mjs list --tool semrush                # 只读节点列表，不耗配额
node backlink/scripts/tools-share-node.mjs probe --tool semrush --nodes 1,2,3 # 逐个真的启动，找一个能用的
```

`probe` 只验证「这个节点现在能不能进去」，不验证「这个节点会不会被限额」——面板配额读数
和每日报告限额是不是同一个口径没有验证过，别把 `probe` 的 recommendation 当成保证。

### 先解决一个错误结论：侧栏不是「看不见」，是在 shadow DOM 里

**之前判定「Semrush 侧栏看不到」是错的**——`state --source ax` 报 `interactive: 0`、
`querySelectorAll('a')` 只返回页眉页脚的营销链接，**都是因为侧栏是 custom element，
导航藏在 `shadowRoot` 里**。必须递归穿透 shadow DOM 才读得到：

```js
(() => {
  const items = document.querySelectorAll('snav-sidebar-ribbon-item, snav-sidebar-list-item');
  return [...items].map((el) => {
    const link = el.shadowRoot?.querySelector('a');
    return link && { label: el.textContent.trim(), href: link.getAttribute('href') };
  }).filter(Boolean);
})()
```

用这个方法一次性多挖出 **15 个之前完全没记录的页面**，总数从 81 → **102**。

**通用教训**：`querySelectorAll` 返回空 ≠ 页面上没有那个东西。
现代面板大量用 web component，**判"没有导航"之前先查 shadow DOM**。

### 关键词魔法工具：指标不是配额门禁，是渐进水合

**这一条推翻了本文件早先的记载。** 早先记的是「搜索量 / KD / CPC 三列返回『不可用』，
要点『刷新指标』才补齐、大概率消耗配额」。**不对。**

那个「不可用 / 要更新指标数据，请刷新」是**页面渐进水合的中间态**——等解析结果稳定下来
指标就全有了。

⚠️ **别把这条读成「凡是空的都是水合中间态，等一等就有」。** 同一批实测里还有并列的另外几种：
页面本身不提供表格的 `chart-only`（等多久都不会有表）、要人先贴输入才产出的 `requires-input`、
压根不是报表路由的营销页，以及被节点限额换掉表体的限额页（换节点，不是等）。
判据形状和分辨方法见 backlink Skill 里 id 为 `readiness-must-bind-to-this-query` 的那条 law。2026-08-28 两次实测（种子词 `nonogram` 与 `tower defense`），
各 100/100 行的搜索量、KD、CPC 全部拿到，`metricsPending: 0`。

**为什么会记错**：第一次抓取时正好落在水合中途，而当时的解析器又有个 K/M 后缀 bug
（`27.1K` 被 `Number()` 变成 `null`），两件事叠加，看起来就像"指标被锁住了"。
`captureStable` 的「连续两次解析结果一致才收下」正是为这种情况存在的。

**含义**：批量扩词可以一次把词表和指标一起拿到，不需要分两步。
用 `semrush-report.mjs --report keyword-magic`。

#### 前提：这 160 次 hidden 读为什么敢叫「诚实」

因为它们跑在**从未 foreground attach 过（即建时就是 background）的会话**上。
**一次 `--window foreground` attach 会把该标签页的 `document.visibilityState`
永久锁死在 `visible`**，~~之后 hidden 造成的一切降级对协议完全隐形~~。
**规则和铁证（同一窗口两个标签页同时 `visible`）的权威版本只写在
backlink Skill 里 id 为 `hidden-tabs-do-not-hydrate` 的那条 law 里
（协议条目 + Experiment E + Experiment F），本文件不复述，只指路。**

⚠️ **2026-08-29 收窄（Experiment F）：划掉的那半句是过度断言。**
钉死是真的，但**被钉住的标签页不是 hidden 冒充 visible——它真的按 visible 调度**。
1.5 秒内的 `requestAnimationFrame` 帧数：建时 foreground、已停泊的标签页 **181 帧**
（`vis=visible`、`focus=false`），建时 background 的 **0 帧**（`vis=hidden`），
当前活动标签页 **181 帧**。所以它不能充当 hidden 样本，理由是「它确实是 visible」，
**不是「它的读数被污染了」**。
**判据是「这个标签页建时是哪种 window 模式」，不是「这个会话现在是不是前台」**：
建时 foreground → 终身钉死 `visible` 且真的 visible；
建时 background → 终身诚实 `hidden`，事后补一次 foreground 导航也救不回来。

**方法学（这才是可迁移的那部分）：不要只读页面报告的状态，要读页面产出的行为。**
`visibilityState` 是一个**可以被钉住的声明**，rAF 帧数是一个**行为事实**。
仪器洁净度还要**每次读数自证**：同一次 eval 里用
`Object.getOwnPropertyDescriptor(Document.prototype,'visibilityState').get.call(document)`
取绕过实例覆写的原生值，并核 `String(document.hasFocus)` 是不是 `[native code]`。

**被作废的观测保留在案**：发现者据此**作废了自己的三次运行**——150 次标着 hidden、
实际读到 visible 的读数。它们被**重新归类为 visible 读，没有被抹掉**。
⚠️ **收窄**：重新归类是对的，「作废」下重了——那 150 次读**采到的数据有效**，
错的只是它们头上「这是一次 hidden 读」的标签。**改标签、留数据，不要当没测过重跑。**
**这条收窄只适用于「假 visible 污染」这一类。** 同一周里因**早停判空**、
**目标未生效**而作废的记录**不受影响，仍然成立**，不要一锅端撤销。

#### 顺带验证：「表元素在、0 行」这个中间态确实存在且会自行解决

`kw-canva-hidden` 第 1 次读是 `tables=1, th=0, rows=0`，**下一轮就变成 `th=19, rows=100`**；

| 一万域名 / 14 列榜单本身 | **未找到** | `ranking` / `websites` / `topsites` / `leaders` 全部静默重定向到 `#/digitalsuite/ai-brand-visibility/home` |

#### 复测协议的新增一条：轮询间隔降到 600–700ms

全程 **1400+ 次读里只有 6 次 `vis=visible`**——因为另一个 agent 的 `semrush-nav` 标签页
一直占着 Chrome 的活动标签；第一次运行还被别人直接把 `similarweb-nav` 会话关掉了
（日志里出现 `No active session`）。

**`visible` 是约 3 秒的短脉冲，6 秒轮询几乎必然错过它。** 实测下来，
**把轮询间隔降到 600–700ms 是唯一能采到 visible 读的办法**。它不缩短轮次、不放宽判据，
只是把同一段等待采得更密。附带一个推论：**「同一个 visible 窗口内连续 3 次」这个要求，
只有在 600–700ms 的采样密度下才够得着**；三次读分散在三个不同脉冲（或三个会话）里
属于跨窗口证据，**不满足**这条。

#### 两条结论的复测判定

| 结论 | 判定 | 证据 |
|---|---|---|
| `#/premium-features/home` = `route-exists-content-empty` | **维持，但强度打折（未完全达标）** | 3 次独立 visible 读（3 个会话、约 40 分钟跨度），全部 `mainLen=0 / bodyLen=209 / title=高级版功能 / hash 未漂移`；合计 **821 次读形态恒定** |
| 网站区段（Segments）只渲染导航壳 | **维持，已达标**（`empty-confirmed-visible`） | 单个 visible 窗口内**连续 3 次**读到 `mainLen=0 / bodyLen=209 / title=网站区段` |

**高级版功能那条必须如实标注「未完全达标」**：协议要的是「**单个 visible 窗口内连续 3 次**」，
而它每次 visible 脉冲只采到 1 次读就翻回 hidden，那 3 次是**跨会话**的。
复测方自己拒绝把它写成达标——**这个分寸要保留，下游不要把它读成 `empty-confirmed-visible`。**

**但它有一个合理的补强论证**：高级版功能和网站区段**共用逐字节相同的 209 字符外壳**，
而网站区段是**达标**的，说明**同一个外壳在确认的 visible 状态下就是这个样子**，
所以高级版功能那 3 次读是**真实渲染结果，不是隐藏态伪影**。再叠上本节开头的对照实验
（Similarweb 隐藏页照常水合），这里的空**本来就不能**用 hidden 解释掉。

### SPA 空白页：已解决，而且解法一直就在代码库里

**根因**：`opencli browser <s> open "<带 hash 的深链>"` 会对哈希路由做**整文档加载**，
SPA 在代理后面启动成空壳。**这不是代理坏了，是打开方式错了。**

**正确姿势**（30+ 个页面验证过）：

```
1. launchTool() 经面板落到工具 origin
2. 在已启动的 SPA 内部导航：eval 里 location.href = ORIGIN + '#/<route>'
3. wait 20–22 秒再读
```

**这正是 `backlink/scripts/lib-tools-share.mjs` 里 `gotoInTool()` 一直在做的事。**
`similarweb-query.mjs` 从来就没被这个问题挡住过——**被挡住的只是绕开它、手敲 `open` 的临时调用。**

> **教训**：遇到"平台限制"先查代码库里现成的脚本是怎么做的。
> 上一轮花了大量时间"攻克"一个早就解决了的问题。

### 未知路由静默重定向：**看到内容 ≠ 功能存在**（2026-08-28 实测）

**Similarweb 面板对未知路由不报 404，它会静默重定向到 `#/digitalsuite/ai-brand-visibility/home`。**

后果只有一句话，但它推翻的是一整类做法：

> **「打开一个猜测的路由、看到了内容」不能证明这个功能存在。**
> 你可能只是被送到了 AI 品牌可见性页，而那页永远有内容。

**唯一有效的判据**：探测之后核对 `location.hash` 还是不是你请求的那一条。
**落地 hash 变了 = 该路由不存在**，内容区多丰满都不算数。

实测两例：`#/digitalsuite/agents/home` 和 `#/digitalsuite/ai-studio/home` 都落到
`#/digitalsuite/ai-brand-visibility/home`——据此才判定本账号没有 AI Agents 那条线。

**这个陷阱是单向的**：它只制造**假阳性**。反方向的结论——「打开后内容区是空的」——
不受影响，因为重定向的落点本身是有内容的页面。所以高级版功能、网站区段那类
「空态」结论不用重查，需要重查的是「打开后看到了内容，所以这个功能存在」那一类。

**对既有档案的影响**：2026-08-27 那一轮的 73 条路由 / 30 页取数**没有记录落地 hash**。
逐条审计结果写在 JSON 的 `liveAudit.evidenceAudit` 里（共审 60 条，3 处证据方式受影响，
已就地标注、未删除）。侧栏功能本身**已由 2026-08-28 的逐项点击 + 记 hash 重新确认过一遍**：
19 项里 18 项取到了路由（转化分析那次点击没生效，路由停在上一页），完整路由表在 JSON 的
`liveAudit.sidebarRoutes`。

**顺带两条入口事实**：面板真实首页是 `#/activation/home`；`#/home/dashboard` 和
`#/digitalsuite/home` 都渲染成空壳（body innerText 长度 0），刷新多轮也不出内容。

### 三条踩过的判据坑

| 坑 | 真相 |
|---|---|
| **刷新解决不了导航问题，还会帮倒忙** | 连续刷新会**短暂把左侧导航整个搞没**，导致 11 个页面误报"找不到导航项"。**正确做法是重试点击，不是重试页面**（6 次点击重试 + 6 秒间隔，11 个全部恢复） |
| 用 `innerText` 长度判断页面是否卡住 | **这个 SPA 上不成立**。多个页面正文只有 500–600 字符却渲染了完整正确的数据——**因为图表是 SVG/canvas，不进 innerText**。阈值从 700 降到 260 才对 |
| URL 里带 `selectedTab=` 就能切标签 | **对已挂载的页面无效**，SPA 会保持自己的 tab 状态。**标签必须点** |

> 上一条对刷新规则是个重要补充：**页面卡加载 → 刷新；导航项找不到 → 重试点击，别刷新。**

## 四·五、API / MCP：整条线判死，别再试（2026-08-27 核实）

**这一节的结论是硬的，不是"取决于权限"。**

### 通用判据（最值钱的一条，先记住）

> **共享账号代理形态下，任何以「账号级 API key / OAuth 授权」为前提的接口，一律不可用。**
>
> **代理面板出借的是「会话」，不是「账号」。** API key 和 OAuth 同意页都住在账号设置区，
> 面板不会把它们递出来；绕过面板去取 = 绕过访问控制，撞本项目红线。

因此对 Semrush / Similarweb / Ahrefs 三家，**「程序化接口」这条线整体判死。
浏览器抓取不是临时替代方案，它是这个账号形态下唯一正确的方案。**

| 接口 | 需要什么 | 现在能用吗 | 判定依据 |
|---|---|---|---|
| Semrush Analytics API v3/v4 | SEO **Business** 档 + **另行购买** units 包 | **不能** | 官方原文：升级到 Business 后 units 仍为 0；key 只在账号 Subscription Info 页取，且只显示一次 |
| Semrush Projects API v3 | Business + units + API key | **不能** | 同上 |
| **Semrush MCP** | 与 HTTP **共用同一份 units** | **不能** | 仓库实测 `units=0`。**这不是"MCP 坏了"，是这个共享账号根本没买 unit 包**——换客户端、换传输、重连 OAuth 都不会改变 |
| Semrush Trends API | 独立订阅 | **不能** | 本项目无该订阅 |
| Similarweb Data API（REST / Batch v4） | **Business / Enterprise / API-only** 档 | **不能** | API key 从账号 dashboard 自取，面板不给 |
| **Similarweb MCP** | 同上，且与标准 API **共用 data credits** | **不能** | 官方原文 |
| Ahrefs MCP | — | **不能** | 2026-07-18 复验，全接口返回 "Insufficient plan" |

**别再重复的两个动作**：① 试图从面板里"找一下 API key"——面板结构上不会有；
② 走 Semrush MCP 的 OAuth 流程——它会弹出登录页要求授权 Semrush 账号，
这等于代替账号所有者做授权，撞「不代替用户登录」的红线。

**一条官方文档冲突，记录备查**：Semrush 的 `api-access` 页与 KB 说 API 是 Business 级 add-on
且升级后 units 仍为 0；较新的 MCP 页却把 SEO Classic Guru / One Starter 也列为含 50,000 units。
这是官方两处口径不一致（很可能是 Semrush One 新包装没同步到旧页）。
**对本项目无影响——两种口径下我们都拿不到 key。**

### 如果将来自购订阅，值得走 API 的

**Semrush**：`phrase_these`（批量关键词，一次 100 词 / 10 units 每行）是最大收益点，
直接替代 `semrush-keyword.mjs` 的 geo-hop + 节流 + 空壳判据整套；`phrase_all` 一次给**全部国家库**，
直接消灭 `--db` 误用陷阱。域名概览全库版解决"不传 `--db` 数字不可比"的老问题。
**注意 v3 backlinks 端点已 deprecated，真要自购先按 v4 重核字段与计价。**

**Similarweb**：**第一步必须先调三个免费 discovery 端点**
（`/v3/batch/credits`、`/v3/batch/user-credits`、`/v3/batch/tables/describe`）——
官方明示零配额消耗，`tables/describe` 会直接吐出全部虚拟表、metric 和 granularity，
一次性把本文件的未知项补实。Batch API 还能给**面板完全拿不到的 daily 粒度**（面板只有月度聚合）。

### API 也拿不到、只能靠浏览器的

| 能力 | 说明 |
|---|---|
| Semrush 全部 AI 板块 | AI 可见度 7 页、AI 公关 5 页、AI 流量。Analytics API 的 report 清单里**没有任何对应 type** |
| 关键词魔法工具的聚簇 | API 侧最接近的是 `phrase_fullsearch`/`phrase_related`，但聚簇是面板独有 |
| Similarweb `similar-sites` | 未出现在公开端点清单中。`[推测,未验证]` 可能在 `tables/describe` 输出里 |
| 一切写操作与项目态 UI | Projects API 只读，MCP 官方明写 read-only |
| Similarweb 5 个独立产品 | API 席位同样按产品分开卖 |
| **两家的口径差本身** | Semrush 是模型输出、Similarweb 是面板外推，不能相减相除。**API 不会让两个数字变得可比** |
