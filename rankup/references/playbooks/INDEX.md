# 预制流水线（playbooks）

**一句话进来，下一秒该跑什么。**

这一层存在的理由：`SKILL.md` 的总路由表只告诉你「去看哪个文档」，
[`capability-map.md`](../capability-map.md) 只告诉你「有哪些能力」，
各 `references/*.md` 只告诉你「怎么判断」。三者都不回答**「先跑哪个、再跑哪个、
谁能并行、产出喂给谁」**——那是本目录。

真实用户不会说「跑一下 seo-audit.mjs」。他会说「做个研究」「review 一下我的站」
「调研一下这个关键词」，然后期待立刻有事情发生。**读完对应那一节就能开跑，
不需要再读第二个文档**；只有到了判读环节才回去翻判据。

## 选哪条

**判据只有一条：看用户交给你的是什么输入，不看他说出口的名词。**
调研只有三种输入：**一个词**（不管他叫它关键词还是词根，一律是词根）/ **别人的域名** / **什么都没有**。
这张表与 [`research.md` 的 P0 分流表](research.md#分流规则只看输入三种形态)、
`SKILL.md` 段 1 **必须三处一致**。

| 用户大概会这么说 | 他交给你的输入 | 走这条 | 花多久 |
|---|---|---|---|
| 「做个研究」「随便看看有什么能做的」——最模糊的那种 | 判不出来 | [`research.md`](research.md) 的 **P0 分流器** | 按输入分流，不问问题 |
| 「挖点需求」「找方向」「最近有什么能做的」「不知道做什么」「**帮我调研下关键词**」（句子里没有具体的词） | **什么都没有**（「关键词」是结果不是输入） | [`research.md`](research.md) **P1** | 第一小时有产出 |
| 「这个词能不能做」「**调研一下 X 这个关键词**」「围绕 X 挖长尾」「帮我扩词」「我这站还能做什么词」 | **一个词根**——用户给的任何词都是词根；**没给也走这条**，用阶段 0.5 反推 | [`research.md`](research.md) **P2 词根调研** | 搜 → 扩树 → 取量 → 社区验证 → 意图核验 → 折成钱 |
| 「谁在赚钱」「反查这个站」「竞品在做什么」 | **一个域名（别人的）** | [`research.md`](research.md) **P4** | 面板阶段串行 |
| 「review 一下我的站」「查漏补缺」「我这站还差什么」 | **一个站（他自己的）**——**没说域名也走这条**，用阶段 0.0 取址 | [`site-review.md`](site-review.md) **一** | 七组并行，20–40 分钟 |
| 「现在该做什么」「到哪一步了」「check」 | 问的是**进度**不是站 | [`site-review.md`](site-review.md) **二** | 3–5 分钟，零配额 |

**旧编号**：3.0 之前的「P2 这个词能不能做」与「P3 扩词」已合并为 P2 词根调研——
单个词的 KD 回答不了「这棵树值不值得进」，扩树与验证是同一条流水线的前后段。

**「他没给我 X」不是反问的理由，是去挖 X 的信号。**
没给词根 → `research.md` P2 阶段 0.5；没给域名 → `site-review.md` 阶段 0.0。
两处都给了完整回退链，走到最后一档才允许问一个问题。

用户的话同时命中两条（「帮我看看这站还能挖什么词」= 体检 D 组 + P2）时，
**先跑体检拿到现状，再拿现状喂调研**——反过来会用一批没有落点的词去查配额。

## `selection.md` 和本目录的分工

[`selection.md`](selection.md) 不是本目录三条流水线（P1/P2/P4）之外的第四条平行选项，
是它们**更早、更便宜的前置关卡**——判的是不同维度的问题：

- 本目录（`research.md`、`site-review.md`）回答**「把一个方向查清楚」**：一个词根能不能排上去、
  一个站有什么问题、一个域名背后谁在赚钱——本质是数据勘查，会花配额。
- `selection.md` 回答**「这个方向该不该做」**：七道硬闸门（硬约束 / 使用频次 / 痛点证据 /
  付费信号 / 护城河 / 获客可行性 / 量化验证），**越便宜、越能杀死候选的排越前**，前六道闸门
  几乎不花配额，只有最后一道「量化验证」才真正打开配额工具。

**先后顺序**：`research.md` P1 挖出来的候选池、或用户随口抛来的一个方向，应该先过
`selection.md` 的闸门 0–5（零配额）；只有活下来的候选，才把主词当词根交给本目录的
`research.md` P2 词根调研继续花配额验证——`selection.md` 的闸门 6「量化验证」本身就是转手
把候选交给 P2 走完整流水线，不是另起一套查词方法。**不要反过来**：先花配额把词表拉全，
再回头筛硬约束/护城河——六轮 546 次搜索走的就是这条反过来的路，绝大多数配额烧在了后来
被免费判据就能秒杀的候选身上。

用户说「找个方向」「这个方向能不能做」「值不值得做」「选品」「有什么能做的」
「帮我看看这个想法」时，先进 `selection.md`，不要直接跳进本目录任何一条流水线。

## 三条贯穿所有 playbook 的铁律

1. **脚本只采集，判决你下。** 三波重构之后脚本里没有打分器、没有阈值门、没有 verdict
   （`backlink/SKILL.md` 法律 `scripts-collect-ai-judges`）。每个阶段表都有「判读」列，
   指向真正下判断的那份文档。
2. **0 条先开 manifest，再说「没有」。** 配额 429、CAPTCHA、卡加载、改版都产出 0 条。
   「采集失败」和「真的没需求」在证据里是可分辨的——不看就下结论是这套流程最贵的错误。
3. **一个配额工具同一时刻只许有一个采集器。** Semrush / Similarweb 会话名固定
   （`semrush-nav` / `similarweb-nav`），所以**面板阶段一律串行**；零配额的源才并行。

## 写新 playbook 的格式（六段，不要自创）

1. **触发**——用户会说的原话，收几种不同的模糊说法。
2. **产出**——跑完拿到什么，具体到文件与结论形态。
3. **流水线**——固定五列表：`阶段 | 并行/串行 | 跑什么（可直接复制的命令）| 拿到什么 | 卡住了怎么办`。
4. **判读**——每阶段对照哪个文档的哪一节下判断。
5. **省配额**——各步的配额档位与代价，哪些零配额可以放开跑。
6. **收尾**——结论写回 `.rankup/` 的哪个文件。

**禁止出现「按需选择」「参考相关文档」这类表述**——那等于把猜测又推回给下一个读者，
而这一层的全部价值就是消灭那次猜测。
