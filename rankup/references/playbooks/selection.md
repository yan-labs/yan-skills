# 选品闸门流水线：这个方向该不该做

**这个文件回答一件事：一个候选方向，值不值得让 [`research.md`](research.md) 去花配额查清楚？**

`research.md` 回答的是「把一个方向查清楚」——一个词根能不能排上去、能折成多少钱。
本文件回答的是更早、更便宜的问题——**在打开任何配额工具之前，这个方向本身站不站得住脚**。
两者是流水线的前后段，不是互相替代：**selection 管"该不该做"，research 管"怎么把一个方向查清楚"**。
过了 selection 的候选，才把主词当词根交给 [`research.md` P2 词根调研](research.md#p2--词根调研这个词能不能做扩成树)继续深挖。

## 来源与免责声明

本文件沉淀自一次批判性复盘：一位独立开发者做了 6 轮工具站选品调研（546+ 次搜索、20+ 语种），
全部失败。复盘材料：

- `research-retrospective-wave1-6.md`（六轮死因总表、缺失筛选维度、评分偏差审计、数据质量审计）
- `gefei-consult-20260912.md`（哥飞 AI Agent 五轮咨询原话）
- `research-bounty-methodology.md`（社群悬赏 4 篇方法论提炼）
- `scripts/demand-scripts-audit.md`（25 个需求挖掘脚本的能力审计）

三条标注纪律，全文遵守：

1. **实测**——脚本/工具真实跑出的数字，标来源文件。
2. **推断**——复盘或本文件自己的归纳判断，不与实测数字混淆。
3. **未核实**——哥飞对话里引用的具名社群发言（Canen、Liran413、Pieter Levels 转述）、
   "哥飞实战手册"来源，以及哥飞自己工具链给出的具体数字（KD 值、月搜数字等）本身未经第二信源交叉验证。
   凡引用这类内容，本文件逐处标注「未核实」，不得当结论直接采信。

## 为什么排序要倒过来

旧流程：拉关键词表（最贵）→ 看搜索量 → 看 KD → 看 SERP 占用 → 付费意愿（排最后，事实上从没真正筛过）。

这个顺序把 546 次搜索里的绝大多数配额，花在了后来被免费判据就能秒杀的候选身上——
海湾老年照护协调平台打出全轮最高分 8/10，而用户约束文件早就逐字点名"care coordination"
不适合独立开发者（闸门 0 级别的否决，却在评分之后才被发现，且从未被真正标注违规排除）；
日语 AI 简历方向拿着一个 Semrush 数字打出 9.2 分，三次下修到 3.5 才 NO-GO（本该在动配额前就被闸门 1
"使用频次"直接杀掉——写简历这件事一个人几年才做一次）。

**排序原则：最便宜、最能杀死候选的排最前。** 七道闸门里，闸门 0–4 完全不花配额，闸门 5 优先用零配额信号、
只在必要时打开一次轻量面板查询，**只有闸门 6 才真正进入 research.md 的完整配额消耗流程**。

## 七道闸门总览

| # | 闸门 | 判据（二元，硬） | 花配额吗 | 详解 |
|---|---|---|---|---|
| 0 | 硬约束 | 逐条对照约束清单，撞一条即出局；二元判定，不打分、不"虽然但是" | 否 | [§1](#1-闸门-0-硬约束) |
| 1 | 使用频次 | 每天/每周→过；一年几次→杀；几年一次→立即杀 | 否 | [§2](#2-闸门-1-使用频次) |
| 2 | 痛点证据 | 独立抱怨来源 <3 个→杀；必须记录他们现在用什么笨办法扛着 | 否 | [§3](#3-闸门-2-痛点证据) |
| 3 | 付费信号 | 意图=信息型，或 CPC 低于同批中位数且无付费证据→杀 | 否 | [§4](#4-闸门-3-付费信号) |
| 4 | 护城河 | AI 工厂两周内能复制→杀；"UI 更好""更懂用户"不算护城河 | 否 | [§5](#5-闸门-4-护城河) |
| 5 | 获客可行性 | 同类头部产品流量结构非 SEO 主导→与无客服约束冲突→杀 | 尽量不花（优先零配额信号，确认不了才开一次轻量面板） | [§6](#6-闸门-5-获客可行性) |
| 6 | 量化验证 | 两条独立路径互证 + 亲眼看 SERP + Semrush 打折 + 意图核验 | **是**（转入 `research.md` P2 全流程） | [§7](#7-闸门-6-量化验证) |

任何一道闸门判定"杀"，流程立即停止，不进入下一道闸门——**不要因为"已经查到这一步了"就继续往下查**，
沉没成本不是继续的理由。

## 1 · 闸门 0：硬约束

### 判据

对照独立开发者产品约束逐条核对，**任意一条命中即出局**：

- 需要多方协调（如 care coordination、供给侧管理的 marketplace）
- 需要持续人工客服或人工运营
- 不是自助 SaaS（订阅或 Credit）付费模式
- 不是一人可建可维护的规模
- 获客设计上不是 SEO 驱动（例如天然依赖线下、销售团队、平台内购但无 SEO 入口）
- 涉及自己出资投放广告（本 playbook 允许**读**别人的买量数据当信号，不允许**自己**买量）

### 怎么做

1. 把候选方向写成一句话（谁在什么场景下用它做什么）。
2. 逐条对照用户的独立开发者产品约束记忆（如果本机配置了这类全局约束文件，先读它）与本文件开头的硬约束清单。
3. **这一步不打分，是/否两态，不写"基本符合""大方向对"这类模糊结论。**
4. 无论后续要不要继续，报告第一行必须写下这道闸门的结论——这是防复发规则 3（见 [§8](#8-三条防复发规则)）的硬性要求。

### 脚本

无。纯人工核对，零配额、零工具依赖。

### 淘汰话术

> 闸门 0 出局：命中约束「\<原文条款\>」——本方向需要\<多方协调/持续人工运营/…\>，与独立开发者约束直接冲突，不进入评分。

### 为什么排第一

海湾地区老年照护协调平台在 Wave1 打出全轮最高分 8/10、标注"the strongest opportunity found this wave"，
用户约束文件里逐字写着"care coordination"不适合独立开发者——这不是需要延伸解读才能发现的边缘情况，
是最直接命中的案例。它没有在当时被排除，是因为评分先于约束检查执行；直到调研方向整体转轨才自然消失，
**不是因为被识别出违反约束而主动排除**（推断，`research-retrospective-wave1-6.md` §3.1）。
零成本的一步，摆在最前面就能拦下这类候选。

### 判据细化：付费意愿与自助模式可能存在结构性互斥（2026-09-13 补）

逐条核对硬约束清单时，容易漏掉一种情况——某个属性单独看不直接命中任何一条，但它同时是
"这批买家愿意付钱的原因"和"自助无客服模式跑不通的原因"，两者互为因果，不是能取舍的两件独立事情。

> 让买家愿意付费的那个属性（后果重大、需要可采信的凭证/有人担责），往往正是让纯自助无客服模式跑不通的那个属性。

后果越重大（法律责任、资金损失、合规处罚），买家就越需要人工对接、SLA、争议复核这类"有人担责"的信任背书，
这天然要求 sales-led 获客与人工客服，与"自助 SaaS + 无客服 + SEO 驱动获客"的约束结构性冲突——
不是"这个方向做得不够好才需要人工"，是这类买家本身的采购逻辑就要求人工介入，UI 做得再自助也绕不开。

**实例**（`.rankup/selection/` 下 AI 图像溯源与合规检测候选，2026-09-13 判杀）：候选定位是面向机构买家
（保险/电商平台/媒体出版）出具"可采信的 AI 图像溯源凭证"（EU AI Act + C2PA 合规检测）。实测走访三个真实
同类产品——InsightFace deepfake 检测、VerifyReal、Hive Moderation——面向这批买家的产品无一例外是
sales-led 获客（官网原话"Contact our sales team to discuss volume, SLAs, and pricing"，无自助注册与
信用卡开箱流程，CTA 是 Request Enterprise Demo/Contact Sales）。EU AI Act Article 50 官方 FAQ 也明确写明，
买家不能仅靠第三方机器可读标记完成披露义务，最终仍需自己法务/合规团队介入判断——进一步印证这类买家对
"人工答疑与担责"的需求是结构性的，不是产品体验问题，不是更好的自助 UI 能绕开的。命中硬约束两条：
"需要持续人工客服或人工运营" + "获客设计上不是 SEO 驱动"。

**用法**：候选定位如果强调"出具可采信的凭证""帮买家担合规/法律责任"这类信任背书，先问一句——这个信任背书
是不是必须靠人对接（销售触达、合同/SLA 谈判、争议复核）才能建立？是→大概率会同时撞上"需要持续人工客服"
与"获客非 SEO 驱动"两条硬约束，不要指望更好的自助 UI 或更全的自助文档能绕开这个结构性问题。

## 2 · 闸门 1：使用频次

### 判据

| 频次 | 判定 |
|---|---|
| 每天 / 每周 | 过 |
| 每月 | 过，但要看闸门 3 是否支撑得起续订理由 |
| 一年几次 | 杀 |
| 几年一次 | **立即杀**，不必再往下查 |

### 怎么做

问一句：**这件事在目标用户的生活/工作里，天然多久发生一次？** 不是"这个人会用我的产品几次"，
是这件事本身的客观频率。拿不准就找 2–3 条真实使用场景描述佐证（不花配额，靠常识和阶段0.5式的快速搜索）。

### 脚本

无。人工判断为主；拿不准时用 `demand/suggest.mjs`（零依赖）看下拉联想里是否出现"多久一次""几年一次"
类修饰词作为侧面佐证。

### 淘汰话术

> 闸门 1 出局：使用频次=\<一年几次/几年一次\>，低频事件天然没有订阅逻辑（无法支撑月付/年付续订），不进入下一闸。

### 为什么排第二，且零成本却能杀掉一大批候选

六轮调研里两个最终都死于变现的方向，根因都在这里：**日语简历**——多数人几年才写一次一份简历；
**英文发票**——多数个体户一年开票几次，免费版额度往往就够用。两者的表层死因是"竞争太强"或"免费替代品占位"，
但更深一层的根因是**低频事件本身撑不起订阅制的续订逻辑**——一个人几年用一次的东西，你收月费他没有理由留着账号，
收年费他更愿意用完即走（推断，综合 `research-retrospective-wave1-6.md` 与 `gefei-consult-20260912.md` 对发票案例的分析）。
这条判据不需要任何工具、不需要看一眼 SERP，却能在第一步就杀掉一大批"看起来有痛点"的候选。

## 3 · 闸门 2：痛点证据

### 判据

- 抱怨句式搜索（Reddit / X / YouTube 评论区）
- **独立抱怨来源 <3 个 → 杀**（是不同的人，不是同一人多平台重复发帖）
- **必须记录他们现在用什么笨办法扛着**——没有笨办法可记录 = 痛点本身可能不真实存在

### 通用原则：访问平台前先找专门工具，不要自己发明方案

这条原则不止用在闸门 2，凡是要访问社交平台或搜索引擎（Reddit / X / YouTube / B 站 / 小红书 / Google
搜索……），固定优先级：**专门 skill（`agent-reach` / `opencli`）> 现成脚本（`scripts/demand/*.mjs`）
> 自己写代码/临时爬取方案。** 本机已装 `agent-reach`，它是这些平台的指定路由器，其 SKILL.md 的常驻规则
明确写着：该 skill 覆盖到的平台必须走它访问，不要自己发明方案。闸门 2 要查的 Reddit / X / YouTube /
B 站 / 小红书评论区全部在它的覆盖范围内。

### 怎么做

**第一步固定是跑一次 `agent-reach doctor --json`**，看各平台当前实际由哪个 backend 提供服务——
这是 agent-reach 自己的常驻规则（路由会变，今天是登录态明天可能换官方 API，不能凭记忆假设），
再按 doctor 报的 `active_backend` 选对应命令组。以下是一次实测结果（**实测**，2026-09-12，供参考，
以每次 doctor 的实际输出为准，不要把这张表当成永久不变的事实）：

| 平台 | status | active_backend | 用法 |
|---|---|---|---|
| Reddit | ok | OpenCLI（复用浏览器登录态，**不需要 `REDDIT_CLIENT_ID`**） | `opencli reddit search/read/subreddit/hot -f yaml` |
| X / Twitter | ok | twitter-cli | `twitter search "query" -n 10` |
| YouTube | ok | yt-dlp | 提取视频信息与字幕 |
| B 站 | ok | bili-cli | 搜索/热门/排行无需登录；字幕需 OpenCLI |
| 小红书 | ok | OpenCLI（登录态） | `opencli xiaohongshu search/note/comments/feed -f yaml` |
| GitHub | ok | gh CLI | 完整可用 |

把社群悬赏方法论给出的固定搜索词矩阵（`research-bounty-methodology.md` §一）当 query 传给上面的命令：

`alternative to xxx` / `xxx is too expensive` / `is there a tool for` / `manually` / `takes hours` /
`wish there was` / `tired of` / 中文对应「每次都要手动」「有没有批量办法」「有没有便宜一点的替代」

分平台看信号：Reddit（评论区"Same problem""I pay XXX for this"）、X（新模型/新工作流后的抱怨，
比 Google Trends 早几周到几个月出现）、YouTube 教程评论区（"有没有自动化方法"）。

原样记录：`平台 | 谁 | 什么场景 | 现在怎么解决 | 花多少时间/钱 | 链接`。**建证据库不建 idea 库**——
坏例子"做一个 AI 发票工具"，好例子"过去 30 天看到 12 个独立开发者抱怨发票格式合规，现在手动改 XML，
每次花 20 分钟，已经有人在 Fiverr 花钱雇人改"。

### 脚本（补充手段，不是首选）

`agent-reach`/`opencli` 已经是这些平台的默认路由，`scripts/demand/*.mjs` 降级为补充——以下场景仍然有用：
需要把大量抱怨一次性落成结构化 JSON/CSV 做批量统计、要接进 gate-runner 的自动化链路（无人值守跑批，
不适合交互式 CLI）、或者 `agent-reach doctor` 报某平台 backend 异常时的临时兜底。

- `demand/reddit-wishes.mjs`（opencli 或 RSS 兜底；**优先走 `agent-reach` 路由到的 OpenCLI 登录态**，
  不需要配 `REDDIT_CLIENT_ID`——OAuth 分支缺这个 key 跑不了，但那条分支本来就不是首选路径）
- `demand/hn-signals.mjs`（Algolia HN Search API，零依赖；HN 不在 `agent-reach` 覆盖范围内，这个脚本
  本身就是首选）
- 其余平台若 `agent-reach doctor` 报 not ok，再按 `research.md` P2 阶段 5 的命令组临时手动操作

### 淘汰话术

> 闸门 2 出局：独立抱怨来源 \<N\> 个（<3），或找不到任何人正在用笨办法扛着这个问题，证据强度不足以判定痛点真实存在。

### 补充判据（社群方法论的六问法，取交集）

参照 JsonChao 的六问淘汰法（`research-bounty-methodology.md` §一·1.2）：问题是否具体（不是"做内容好累"这种大词）；
是否反复发生；现在已经付出什么；现有办法差在哪；谁付款为什么会换；我能不能找到这批人。
**高赞回复可能已经给出免费解法**——先看这个笨办法是不是已经被一条高赞评论解决了，再判断还剩什么值得做产品。

## 4 · 闸门 3：付费信号

### 判据

- **CPC + 搜索意图分类**（商业意图+高 CPC 的小词 > 免费意图的大词）
- **这批人现在有没有在为笨办法付钱**（外包订单/竞标记录/现有工具的付费墙位置）
- 意图=信息型 → 直接杀；CPC 低于同批中位数且找不到任何付费证据 → 杀

### 核心洞察（哥飞原话，`gefei-consult-20260912.md` 第 4 轮，未核实其工具链数据来源本身，但对话记录真实存在）

> "`invoice api` 140 月搜、CPC $48、意图'商业'——搜的人是一个程序员/技术负责人在找 API 文档，
> 他背后的公司有预算、有付费意愿、有采购流程。140 个这样的人，比 33,100 个找免费发票模板的人，值钱得多。"

> "CPC 和意图一直在我们每次拉的同一张词表里，筛了 546 次每次都跳过。**不是没数据，是没看。**"

### 怎么做

对每个候选词，同时看两个此前从未被系统性使用的字段（它们就在同一张 Semrush 表里）：

1. **意图分类**：交易/商业意图优先，信息意图直接砍（`free resume builder` 90,500/月被 Semrush 分类为
   信息型——用户只是想了解"什么是免费简历生成器"，不是要用）。
2. **CPC 顶部出价**：>$10 极高（B2B/SaaS/金融）、$3–10 高、$1–3 中等、<$1 弱慎重。

再往下做一步旧方法论从没做过的事——**查这批人现在有没有在为笨办法付钱**：外包平台（Freelancer/Fiverr/Upwork）
是否有人花钱雇人做同一件事；同类产品的定价页是订阅制/Credit 制还是永久免费；Stripe 收银台引荐榜上有没有同赛道的站。

### 脚本

- `demand/keyword-value.mjs`（本地计算 CPC / 同批中位数比值，不联网）
- `gefei-ask.mjs`（问 CPC + 意图，走 OpenCLI 驱动已登录 Chrome 问哥飞 SEO Agent，Google Ads Keyword
  Planner 级精度，2026-09-04 实测；本机未配置 `SEO_WEBCAFE_COOKIE`，统一用这条路径，不用需要该
  Cookie 的 `seo-webcafe.mjs chat`）
- `demand/stripe-referring.mjs`（不计配额，查谁的流量走到了收银台）
- `demand/freelance-demand.mjs`（freelancer 子源零依赖，直接看真实成交订单/竞标）
- `demand/serp-query.mjs`（**本机缺 `SERPER_API_KEY` 跑不了**，用 `seo-webcafe.mjs serp` 替代，计 1 配额）

### 淘汰话术

> 闸门 3 出局：意图=信息型/CPC $\<X\> 低于同批中位数，且未找到任何该品类的付费证据（外包订单/收银台引荐/付费定价页）。

### KDRoi 的陷阱（哥飞原话，未核实其推导过程，KD 值为预估非实测）

> KDRoi = 搜索量 × CPC ÷ KD。"如果只看 KDRoi，free 的词反而更高？对，这就是 KDRoi 的盲区——
> 它不区分'意图'。……所以我建议把 KDRoi 用在同意图词之间比较……跨意图比没意义。"

**只在同意图词之间用 CPC/KDRoi 排序，不得跨意图比较，不得把高 CPC 单独当"这个方向能赚钱"的结论。**

## 5 · 闸门 4：护城河

### 判据

**AI 工厂两周能不能复制？能→杀。** 但这只是第一层问题，不是全部——**能挡住 AI 工厂的壁垒，不等于能挡住资本**，
第二层问题见下方"判据再修正：法定强制 ≠ 一人开发者的护城河"。「深度格式/合规本地化」（日本 JIS 简历格式、
沙特 ZATCA 发票合规）曾被列为六轮里唯一反复验证成立的护城河类型，但**这两个样本从未被验证有独立开发者
靠它成功过，只是逻辑推断**——降级标注见下方修正。「我们 UI 更好」「我们更懂用户」一律不算护城河。

### 怎么做

问："这个产品的核心能力，是不是'上传数据/信息 → AI 生成 → 下载'这种通用模式就能覆盖？"
能覆盖 → 杀（Wave4 发现的"AI 设计工厂"15+ 平台，用同一套扩散模型后端 + 程序化 SEO，
为几乎每个"文化×场景×语言"长尾组合在几天到几周内自动生成落地页）。
再问："有没有强制性的政府法令、行业标准、精确到字段级的格式要求，是 AI 文本生成做不对的？"
再追问第三层（2026-09-13 二次修正，详见下方）："这个强制性/格式壁垒会不会把市场做成'全国所有人/企业
都必须买'的规模？" 会 → 大概率已经或即将被资本用免费层铺满，即使 AI 工厂真的做不了，也轮不到一人开发者，
照样杀。**真正能穿过闸门 4 的壁垒，要同时小到资本不屑进场、又硬到 AI 工厂懒得跨越**——这个交集很窄，
不能靠"沾了政府/合规字样"就默认放行。

### 哥飞原话（`gefei-consult-20260912.md` 第 1 轮，逻辑框架未核实是否有实证支撑——第 5 轮它自己承认了这一点）

> "你唯一验证成立的那个模式（日本 JIS 简历、沙特 ZATCA 发票）之所以能活下来，恰恰是因为它不是套利——
> 它有真实的技术复杂度，不是'做个页面填个模板'就能搞定的。这就是你该去的方向。"

**重要限定（第 5 轮哥飞自己的坦白，`gefei-consult-20260912.md` 第 5 轮）**：它后续推荐的德国/波兰/意大利
电子发票方向，明确承认"知识库里没有'我做了德国电子发票工具站并成功了'的案例……我推荐它是基于你们自己验证过的模式
加上市场数据——但'验证过'和'有人成功过'是两回事。你们如果做，就是探路者。" 护城河判据本身可信
（六轮里唯一没被推翻的正面模式），但**具体某个新市场是否真的有这个护城河，仍需闸门 6 的真实数据验证，
不能仅凭"逻辑上应该成立"就跳过后续闸门**。

### 判据细化：只读提取 ≠ 按政府格式签发凭证（2026-09-13 补）

"深度格式/合规本地化"这条护城河容易被误读成"这个领域沾了合规/政府字样，就有护城河"——需要再往下问一层：
产品的输出端到底是**读数据**还是**签发凭证**。

> 只读提取 ≠ 按政府格式签发一份具法律效力的产物。

日本 JIS 简历格式、沙特 ZATCA 发票之所以构成护城河，是因为产品必须**按法定字段结构生成并对接政府系统，
签发一份具法律效力的产物**——生成错了有真实的法律/税务后果，这才是"AI 工厂两周复制不了"的根本原因。
反例是任何"把纸面上已经存在的信息读出来"的产品（OCR/视觉模型提取金额、日期、商家……）——不涉及按任何
强制格式**生成并签发**新的具法律效力文件，本质仍是"上传→AI提取→导出"的通用模式，两周内可复制。
**读数据不是壁垒，签发凭证才是。**

**实例**（`.rankup/selection/` 下收据扫描/费用记账候选，2026-09-13 判杀）：候选逐条排查是否存在等价于
ZATCA 的强制格式义务，未找到——美国 IRS 等主要税务机关对个人/小微企业收据留存的要求是"记录清晰可读、
能在被审计时提供依据"，没有规定必须用特定软件格式或字段结构；候选核心能力精确匹配"上传收据图片→
OCR/视觉大模型提取金额日期商家类别→结构化导出"，且已经被验证复制——Fiverr 上有真实成交的商品化 gig
直接卖这个能力本身（"I will integrate veryfi ocr API for receipt and invoice scanning" $90；另有 $500/68 单、
$100/280 单成交的收据 OCR 项目），SERP 前 8 已有 Wave/bill.com/Dext/Readdle/SparkReceipt 等成熟竞品。
护城河判据本该杀死的正是这种"沾了报税/合规字样，但核心只是只读提取"的候选。

**用法**：遇到任何"这个领域涉及合规/政府格式"的候选，先问一句——产品的输出端，是不是要按政府/行业强制的
字段结构**生成一份新的、具法律效力的文件**并对接官方系统？是→**先不要直接判"可能有护城河"，接着走下面
"判据再修正"这一层**；不是（只是把已有信息读出来、转换格式、做展示）→不构成护城河，不要被"合规"两个字唬住。

### 判据再修正：法定强制 ≠ 一人开发者的护城河（2026-09-13 二次修正）

上面"只读提取 ≠ 签发凭证"这条区分本身没错——产品必须按法定字段结构生成并对接官方系统，比"只读数据"门槛高，
这个判断保留。但**"签发凭证 = 一人开发者的护城河"这一步推论是错的**，被一次跨市场实证调研推翻
（`research-domain-hunt.md`，2026-09-13，5 个调研员 + 哥飞 SEO Agent 咨询）：

逐个查了英国 MTD ITSA（2026-04 强制）、波兰 KSeF（2026-02/04 强制）、比利时/法国/德国 Peppol、
沙特 ZATCA、马来西亚电子发票——**全部被免费层塞满**：FreeAgent／Zoho Books／Clear Books（英国，完全免费或免费档合规）；
iFirma／wFirma／inFakt／Fakturownia（波兰，KSeF 对接全部含在 0–20 PLN/月最低档）；
Accountable／Let's Peppol（比利时，含非营利免费开源）；Abby／Indy／Qonto（法国，国家认证平台且免费覆盖个体户）；
沙特/马来西亚官方门户本身免费，且 Zoho/Bukku 有免费档。**Peppol 明确不允许个人直连**，必须租用认证
Access Point（如 Storecove €0–894/月），租用之后壁垒对租用者本人已经消失。

结构性原因：**强制 = 全国所有个体户/企业必须买 = 市场大到值得融资 = 资本进场 = 免费层出现。壁垒越"法定"，
招来的市场越大，一人开发者越拿不到——法定强制本身就是"这里值得烧钱抢份额"的最强公开信号，而不是护城河信号。**

**修正后的判断方式**：闸门 4 要同时满足两条，缺一不可：
1. 壁垒要真实、AI 工厂跨不过去（原判据，"只读提取 ≠ 签发凭证"这条区分依然适用，用来先过滤掉假壁垒）；
2. 壁垒要小到资本不屑进场——市场天花板越低、越冷门、越依赖持续劳动而非一次性合规资质，资本越不来。
**法定强制类壁垒往往同时把这两条一起废掉：AI 工厂确实跨不过，但资本也来了，一人开发者两头不沾。**

日本 JIS 简历格式、沙特 ZATCA 发票这两个原始正面样本**降级为「未验证」标注**：目前能找到的都只是
"逻辑上这类壁垒应该挡住 AI 工厂"的推断，**没有查到任何独立开发者靠它们成功的案例**（哥飞知识库同样查无——
`gefei-consult-20260912.md` 第 5 轮哥飞自己承认，它推荐的电子发票方向"知识库里没有'我做了德国电子发票工具站
并成功了'的案例……'验证过的模式'和'有人成功过'是两回事"）。遇到"这个领域涉及法定强制格式"的候选，默认姿态
从"可能有护城河，进闸门 6"改为"先假设资本已经或即将进场，去查有没有免费层"——查到免费层就地杀，
查不到才进闸门 6 用真实数据验证。

### 正面样本：监控/聚合/累积型工具（2026-09-13 补，同一份实证调研）

真正能同时挡住 AI 工厂和资本的壁垒形态，实证下来是"持续维护敌对的数据管道"或"无法回填的时间积累数据"，
产品形态是监控/聚合/提醒/历史数据类工具：

- **敌对数据管道**：几十上百个反爬源、无官方 API、随时改版——边际成本不为零且持续发生，AI 工厂"生成后即摊薄"
  的流水线摊不平这种成本；但市场天花板通常是单城市/单平台量级，资本也看不上，工厂不愿跨、资本不屑进，
  同时满足上面两条。
- **无法回填的时间积累数据**：价格历史、成交历史、房源出现/消失时间戳——今天开始抓也要 12–18 个月才有
  可卖的产品，AI 工厂造不了假历史，先发者赢、后来者永远追不上。

**实证支撑**：紧张租房市场的付费房源秒级提醒——荷兰 Stekkies／RentSlam／WoonBusters、都柏林 HomeScout
（单个创始人创立）、德国 6+ 家（ImmoVorsprung 等）、布拉格／华沙／巴塞罗那／哥本哈根／苏黎世，**8 个国家、
10+ 个互不相关的独立团队各自验证了同一模式**（创始人、定价、技术栈均不同），是教科书级的"多独立验证"而非
"一家工厂铺货"。Keepa 型历史价格追踪——Keepa（Amazon，$19/月，DR 74）、aucfan（日本雅虎拍卖，已上市）、
Cardmarket 生态的 Flipzi／TCGGraph、Vinted 生态的 VintPulse 等独立开发者产品。

**代价（不能回避，进入闸门 6 前要向用户挑明）**：
- **敌对维护，不是零维护**：对方会主动改站点结构、封 IP、限速——Vinted 2026-07 起已对自动重发限号 24 小时。
  这类壁垒的本质是**每周固定的工程劳动**，与"零维护"约束冲突，需要改写成"零客服、零销售，允许每周有限
  工时的工程维护"。
- **ToS 灰区**：荷兰有 Funda/Gaspedaal 数据库权判例、Amazon 对 Keepa 式扩展抓取存在争议（未起诉）。
  现存站的存活证明"技术反爬 + 轻量抓取 + 不展示原始数据库"实践中可行，但不是零风险，进这类方向前要让
  用户明确表态"接受"还是"不接受"法律灰区。
- **与"纯 SEO 获客"直接冲突，闸门 4 在这里如实摆出来，不替闸门 5 下结论**：同一份调研里，这类站的 Google
  自然搜索占比普遍偏低——Stekkies 搜索 24.5%／直访 44.5%，RentSlam 搜索 26.6%／直访 48.8%，Keepa 搜索
  14.6%／直访 75.4%，Vendoo 搜索 7.7%／直访 73%，跨样本区间约 7.7%–26.6%。这类产品的第一批用户通常来自
  一次性社区播种（Reddit 子版块、本地 Facebook 群、Product Hunt），SEO 至多是 12–18 个月后才起作用的
  第二引擎，不是启动引擎。这个模式能不能进场，最终要看闸门 5"获客可行性"能不能接受这种获客结构——
  闸门 4 判定护城河成立，不代表闸门 5 会放行，两道闸门都要过。

### 脚本

主要靠人工判断；辅助用 `demand/aitdk-lookup.mjs`（默认 webcafe provider 免费）查同类产品的域名画像，
看现有竞品是不是清一色的"套壳生成器"。

### 淘汰话术

> 闸门 4 出局：核心能力可被"上传→AI生成→下载"模式在两周内复制，无强制格式/合规壁垒，唯一差异化是 UI/文案/服务态度，不构成护城河。

## 6 · 闸门 5：获客可行性

### 判据

**只能靠蹲社区/发帖/人工运营才拿得到量 → 与无客服约束冲突 → 杀。**

### 怎么做

查 1–3 个同赛道头部产品的真实流量渠道构成（Search / Direct / Social / Referral / Paid 占比）。
Search（非品牌）占大头才继续；Social/Direct 占大头说明这个品类的获客靠的是社区运营或品牌传播，
独立开发者在无客服无人工运营的约束下复制不了。

**优先用零配额信号先判断**（founder 操盘史搜索、`site-network.mjs`、`ads-transparency.mjs` 持续投放情况），
拿不准再打开一次 Similarweb 面板做单次 channels 报表确认，不要把这一步做成阶段 5 那种大规模面板消耗。

### 两个警示案例

**荷兰语每日问答**（`research-retrospective-wave1-6.md` §2.2）：头部站 dagelijkse.nl 151K 月访问，
**79.8% 来自 Facebook，只有 5.5% 是直接流量**（实测，Wave5 原始报告转述）。这类品类即使流量真实存在，
获客主渠道也不是 SEO，复制不了。

**filetrove.app**（哥飞第 3 轮续，`gefei-consult-20260912.md`，实测数字来自哥飞工具链，未做独立交叉核实）：
DR 0、5 万月访问、搜索占比仅 10.3%、平均停留 18 分半、跳出率 18.7%——"这是产品力驱动增长的标本，
不是 SEO 驱动增长"。即使这个产品活得很好，它验证的获客模式（口碑/沉浸式使用/书签直接打开）
也不是无客服无人工运营+SEO 驱动这套约束下可复制的路径，只能当作"这个品类有人做成了"的旁证，
不能当作"SEO 能把它做起来"的证据。

### 脚本

- `similarweb-query.mjs --report channels`（backlink Skill，面板配额，单次确认用）
- `demand/site-network.mjs`（零依赖）
- `demand/ads-transparency.mjs`（零依赖，查同类是否持续投放）
- founder 操盘史搜索：品牌名 + `founder`/`MRR`/`SEO`/`launch`，在 X/Reddit/IndieHackers 搜（`/agent-reach`、`/anysearch`）

### 淘汰话术

> 闸门 5 出局：头部产品 Search（非品牌）流量占比 \<X\>%，主渠道是 \<社交/直接/联盟\>，获客假设与"无客服无人工运营、SEO 驱动"约束不匹配。

### 判据

**到这才动配额。** 两条独立路径互证 + 亲眼看 SERP + Semrush 泛词打 3 折 + 「AI」前置才有量（日语等语种的构词校准）。

### 怎么做

不再重复 research.md 已经写清楚的操作细节。

### 校准值（衔接 research.md 的既有判据，不重复定义，仅在此提示"闸门 6 一定要用"）

- Semrush 对泛词系统性高估约 **3 倍**（实测：日语 `履歴書 作成` 报 27,100/月，Trends 锚点法折算上限约 8,960/月）

  （构词/词序陷阱不是日语独有，任何目标语言进入闸门 6 前都要用 `suggest.mjs` 系统测试至少 3–4 种词序变体）
- 决定生死的数字，**单一数据源不得直接导出 GO/NO-GO**——两条路径未能互证时，方向状态只能是"待定"

完整校准值表见 [§10](#10-校准值速查表)。

## 8 · 三条防复发规则

复盘查出的三个方法论缺陷，每条对应一条具体规则，不是"要更严谨"这类空话。

### 8.1 CPC 不是付费意愿的等价替代

**背景**：付费意愿曾写进方法论（Wave1 综合报告，权重 20%），随后从 Wave2 起消失，
Wave5 起用 CPC 顶替，但 CPC 衡量的是**广告主买量意愿**，不是**用户订阅付费意愿**——
两者在发票案例里是同一个问题的两个不同答案（`research-retrospective-wave1-6.md` §2.1）。

**澄清（避免误读成自相矛盾）**：闸门 3 仍然用 CPC，但用法不同——**它是配合意图分类做的筛选信号，
不是付费意愿的等价替代**。真正的付费意愿证据必须来自闸门 3"这批人现在有没有在为笨办法付钱"这一问的实证
（外包订单、收银台引荐、竞品付费墙）。

**具体规则**：任何报告中出现 CPC 数字，必须与"意图分类"字段同框出现，不允许单独引用 CPC 作为
"付费意愿已验证"的证据；CPC/KDRoi 只能在**同意图词之间**排序，不能跨意图比较（KDRoi 盲区：
`free invoice generator` 的 KDRoi 反而比 `invoice api` 高，但前者的用户不想付钱）。

### 8.2 未过闸门 6 不得给分

**背景**：日语 AI 简历方向在同一轮内三次下修：9.2 → 6.5 → 3.5，最终 NO-GO
（`research-retrospective-wave1-6.md` §3.3）——顺序被颠倒了，应该是先验证再定分档，
实际执行的却是先给一个耸动的分数、再花三轮篇幅把它拆掉。

**具体规则**：闸门 6（量化验证，两条独立路径互证）完成之前，**不得给出任何数字分数或"X/10"式结论**。
报告只允许三态标注：闸门 0–5 各自"过/杀"+ 杀在哪条；闸门 6 完成前一律标"待定"；
闸门 6 完成后只写 GO/NO-GO（附理由清单），不写分数。

### 8.3 闸门 0 在任何评分之前执行

**背景**：Wave1 打出全轮最高分 8/10 的海湾老年照护协调平台，用户约束文件里逐字点名
"care coordination"不适合独立开发者，却从未在综合报告里被标注"违反约束、应排除"
（`research-retrospective-wave1-6.md` §3.1）。

**具体规则**：闸门 0 必须是报告开头的第一行，且必须逐字引用被命中（或确认未命中）的约束条款——
"闸门 0：通过/出局，命中条款：\<原文\>"。**没有这一行的报告视为无效**，即使后续闸门 1–6 全部通过也不算数，
退回重做。

## 9 · 候选生成器（闸门体系之外）

七道闸门筛的是"已经有的候选"，这一节回答候选从哪来——**在旧方法论"拉关键词表找洼地"之外的另一条路**。

### 领先指标法

搜索量是**滞后指标**——等一个词有搜索量了，AI 工厂早就铺满了；**买量和榜单是领先指标**。

逻辑链：**有人肯为某需求花钱买量 → 说明 LTV 撑得住获客成本 → 后续才会有人开始搜 → 搜索量出现**。

路径：**谁在买量/谁在冲榜 → 这个需求是什么 → 网页端有没有人做 → 进闸门 1**。

额外好处：没人肯为它买量的需求本身就不值钱——这条路径本身已经把闸门 3 的一部分工作在生成阶段就做完了。

**重要限定：我们自己不买量，只读别人的买量行为当信号。** 这条生成器不改变硬约束里"不买量"的红线，
它只是把别人已经花出去的钱当作免费情报来源。

### 移动端 App 信号（只当信号源，不主张转做 App）

移动端 App 的需求可能就是网页端的需求——App 冲榜说明需求已经被验证过，而网页版可能还没人做。
但技术栈跨度大（原生开发 vs Web SaaS），**本 playbook 只把 App 数据当信号源，不主张转做 App**：
看到某类 App 在 App Store 付费榜/畅销榜稳定占位，把它的品类词当候选，进闸门 0，不是转去学 iOS/Android 开发。

### 脚本化工具：`scripts/select/leading-indicator.mjs`（候选生成）+ `scripts/select/gate-runner.mjs`（闸门判定）

上面两条生成路径已经封装进 `leading-indicator.mjs`：`scan --source ads|appstore|gplay|stripe` 调用对应
demand 脚本产出候选并落盘去重，`report` 负责聚类/巨头过滤/工厂识别/导出。判定仍然是 `gate-runner.mjs`
的 `gate <0-6> --pass/--kill` 系列命令在做（自动写 `.rankup/decisions.md`/`rejected.md`，见 §13「收尾」），
两个脚本各司其职，产出不互相覆盖——具体参数见各自 `--help`。

**信号源族**：`ads`/`appstore`/`gplay`/`stripe` 四个信号源，`appstore` 与 `gplay` 同属一族 `app-charts`
（同一个"App 冲榜"观测的两次采样点），`ads`、`stripe` 各自独立成族。**"多个独立方法论撞到同一方向"
这个硬信号只能看跨族命中**（`report --cluster` 的 familyCount≥2），**不能看命中源数**：appstore+gplay
都命中同一候选只算同族内 1 族，实测目前真实数据里跨族命中是 0 次（ads/stripe 候选量太少，撑不起与
app-charts 族的印证）——"多个信号源汇聚""三个独立信号源汇聚到同一方向"这类说法已被证伪，**只有跨族
命中才算交叉验证，同族内多店命中不算**。

**聚类只做同名/同域名去重，不做模式识别**：早先设计过用"开发者名"当第二把聚类钥匙去抓"同一家公司跨源
撞车"，真实数据证明代工壳公司挂靠同一账号做不相关 App 太常见，链式传递会把无关产品误并，已移除——
**"聚类能发现跨垂类模式"这个说法已被证伪**，精确名字/域名匹配抓不到"措辞不同但其实是同一类需求"这种
模式，字符串匹配做不到，交给人或 LLM 通读 `report --export-jsonl` 导出的紧凑 JSONL（scan 时已自动写一份）。

**工厂识别**（`report --factories`，阈值 `--min-factory-products` 默认 2）：同一个开发者账号在当前数据集
里挂了 ≥ 阈值个候选，标成"疑似工厂"，提醒去核实是不是同一套模板批量复制到了不同垂类（真实案例：Glority
把"拍照识别+估值"用马甲公司 Next Vision Limited 复制到 9+ 个垂类——字符串匹配抓不出这种别名/DBA，仍需
人工翻开发者页核实）。**工厂 ≠ 巨头**——`--giants` 判"这一个产品体量大/发行商是知名大厂"，`--factories`
判"这个开发者名下挂了好几个产品"，两套判据/名单/阈值完全独立，不要混着看。同一模式跨垂类出现有两种
相反含义：**多个独立团队各自验证了同一模式**（好信号，见 §5 闸门 4"监控/聚合型工具"正面样本）vs
**一家工厂批量铺货，地已经被收割**（坏信号）——区分看开发者是不是同一个账号/公司，不是看模式本身像不像。

**信号源覆盖差异（用工厂识别前先确认字段有没有）**：appstore 的 `extra.artist` 每次 scan 都带；**gplay
的 `extra.developer` 只有 `--ranking` 模式才带**，默认搜索/分类列表模式（字段是 `position`）拿不到——
scan gplay 时不显式加 `--ranking`，gplay 侧的工厂识别、以及"跨商店同名匹配"这条巨头过滤补救路径都会
测不出来；ads 只有 `creatives` 子命令有开发者字段，`advertisers` 子命令本身就是广告主，没有独立开发者
字段；stripe 只有域名，不参与工厂识别。

**巨头过滤只在 `scan` 时生效，`report` 不回溯**：appstore/gplay 默认过滤掉命中已知巨头名单、或跨商店
同名匹配到对面已判过巨头的候选（`--no-filter` 关闭），但只作用于这次新落盘的候选——已经 scan 过的历史
候选不会因为后来更新巨头名单而重新过滤，想重新过滤要重新 scan。

**`--ads-mode` 必填**（仅 `--source ads`）：显式声明这次透传的子命令是 `creatives` 还是 `advertisers`，
跳过字段探测；不传会从透传参数自动识别，两条都没有才报错，不会静默瞎猜。ads/appstore/gplay 连续快速
查询可能触发 Google 的异常流量检测并弹验证码/限流，脚本会侦测并进入跨进程冷却（`<out-dir>/block-state.json`），
冷却期内拒绝再发请求——看到"🚫 被墙"不要立刻重跑，等冷却结束或换个信号源。

### 三问链：候选生成之后，先按顺序问完这三句再决定进不进闸门 0

①**有人在搜吗**——这个方向有没有对应的可搜索关键词，不是只有 App/广告信号。
②**有人赚到钱吗**——现有玩家有没有真实收入证据（付费墙、收银台引荐、外包成交），不是"看起来有人在做"。
③**还有位置吗**——SERP/榜单前排是不是已经被巨头或工厂占满。**知道有人赚钱 ≠ 还有位置**：①②都成立
只说明这不是伪需求，③才是决定还要不要花时间往下走的关键，最容易被漏问。

## 11 · 证据强度分层

用于闸门 2（痛点证据）与闸门 3（付费信号）判定"这条证据算不算数"：

| 层级 | 例子 | 能得出什么 |
|---|---|---|
| 点赞 / 收藏 / 说有兴趣 | Reddit 帖子获赞、"这个想法不错" | 只说明"引起了注意"——不算数 |
| 愿意提供真实材料 | 愿意把自己的数据/文档发过来 | 说明问题值得他花时间沟通——不算数 |
| 实际试用并反馈 | 用了 MVP 并给出具体意见 | 方案进入了真实任务——不算数 |
| **愿意为约定结果付款** | 下单/订阅/付费试用 | **开始出现交易证据——算数** |
| **再次使用 / 续费 / 主动推荐** | 复购、续订、转介绍 | **才能判断长期价值——算数** |

**只有后三档算数，前两档不得写进"付费证据"栏。** 明确警告：`reddit-wishes.mjs` 一类信号（许愿句式、
"is there a tool that"）证明的是**意愿**，不是**付费**，属于闸门 2 的痛点证据来源，
**不得混入闸门 3 的付费证据**——一个人可以许愿一百次也不掏一分钱。真正的付费证据来自
`stripe-referring.mjs`、`freelance-demand.mjs` 这类脚本，或竞品定价页/付费墙的直接观察。

（分层来自 `research-bounty-methodology.md` 悬赏 1 JsonChao 提炼，原文用词略有精简，判据未改动）

## 12 · 工具清单与可选加速通道（6 个未配 key 均非必需）

本机未配 6 个 API key（`SERPER_API_KEY` / `TABAPI_KEY` / `GITHUB_TOKEN` / `PRODUCTHUNT_TOKEN` /
`IGDB_CLIENT_ID` / `REDDIT_CLIENT_ID`，见 `scripts/demand-scripts-audit.md`）。**这 6 个 key 全部不是
能力缺口**——每一个都只是"已经有免费路径之外，另一条付费/官方替代通道"，配了跑得更快、限流更宽，
不配同样能跑完整七道闸门。逐个说明当前实测可用的免费路径：

| Key | 它本来是什么 | 免费替代路径（实测可用） |
|---|---|---|
| `REDDIT_CLIENT_ID` | Reddit 官方 OAuth API 的替代通道 | 不需要配：Reddit 走 `agent-reach` 路由到的 OpenCLI 登录态即可，见 §3 速查表（**实测**，2026-09-12） |
| `SERPER_API_KEY` | 付费 SERP 抓取 API 的替代通道 | `opencli google search "<query>" --lang <lang> --limit 10 -f json`（本项目实战验证过）；也可用 `seo-webcafe.mjs serp`（计 1 配额） |
| `GITHUB_TOKEN` | 提高 GitHub API 限流上限的替代通道 | `gh` CLI 本机已登录，直接可用；想要更高限流一行 `gh auth token` 就能取得，不需要单独去 GitHub 后台申请 |
| `TABAPI_KEY` | 官方数据源的付费替代通道 | 脚本默认 `--provider webcafe`，免费可用，吃共享配额而非硬失败 |
| `PRODUCTHUNT_TOKEN` | ProductHunt 官方 GraphQL API 的替代通道 | 脚本默认 provider 免费可用，自动降级浏览器路径，数据更全，不算硬失败 |
| `IGDB_CLIENT_ID` | 游戏方向专用官方数据源 | 只影响游戏方向；换 `--source steam/itch/poki` 同样能跑 |

逐闸门影响：闸门 0/1/5/6 完全不涉及这 6 个 key；闸门 2/3/4 各自有一个"配了更快"的可选分支，
不配就走上表对应的免费默认路径，**不是跑不了，只是少一条更快的选项**；候选生成器阶段同理（见 §9 脚本表）。

**结论**：七道闸门体系在这 6 个 key 全部未配的情况下完整可用，不构成能力缺口——遇到"缺 XX key"字样，
一律理解成"有更快的路可以配，但现在这条免费路径已经在跑"，不要理解成"这一步做不了"。

## 13 · 流水线速查（六段格式）

按 [`INDEX.md`](INDEX.md) 约定的固定五列格式汇总，细节见 §1–§7：

| 阶段 | 并行/串行 | 跑什么 | 拿到什么 | 卡住了怎么办 |
|---|---|---|---|---|
| 生成 | 并行 | `ads-transparency.mjs` / `appstore-charts.mjs` / `boards.mjs` / `stripe-referring.mjs` / `game-newtitles.mjs` 等零配额榜单脚本 | 一批"有人在买量/冲榜"的候选方向 | 没有候选池时改用用户直接给的一个方向（走 `research.md` P0 分流"一个词"入口） |
| 0 硬约束 | 串行，主线判读 | 对照约束清单逐条核对 | 通过/出局 + 命中条款 | 出局直接停，不进闸门 1 |
| 1 使用频次 | 串行，主线判读 | 判断需求天然触发频率 | 通过/出局 | 拿不准就找 2–3 条真实使用场景佐证，不开配额工具 |
| 2 痛点证据 | 并行（零配额） | 先 `agent-reach doctor --json` 选路由，按 backend 用 `opencli reddit/xiaohongshu` / `twitter-cli` / `yt-dlp` / `bili-cli` 跑固定搜索词矩阵；`hn-signals.mjs`（HN 专用）+ `reddit-wishes.mjs`（补充/批量场景）兜底 | 独立抱怨来源计数 + 笨办法记录 | <3 个独立来源直接杀，不许"再搜一轮凑数" |
| 3 付费信号 | 串行（零配额为主） | `keyword-value.mjs` / `gefei-ask.mjs` / `stripe-referring.mjs` / `freelance-demand.mjs` | CPC + 意图 + 是否已有人为笨办法付钱 | 意图=信息型直接杀；CPC 低且无付费证据也杀 |
| 4 护城河 | 串行，主线判读 | 人工判断"AI 工厂两周能否复制" + `aitdk-lookup.mjs` 查同类产品画像 | 护城河类型判定 | 只有"UI 更好""更懂用户"这类理由 = 无护城河，杀 |

### 收尾

把每个候选的七道闸门结果写进 `.rankup/decisions.md`：

```
## <候选方向> 选品闸门 (YYYY-MM-DD)
闸门0 硬约束：通过 / 出局，命中条款：<...>
闸门1 使用频次：<每天/每周/一年几次/几年一次> → 过/杀
闸门2 痛点证据：独立来源 N 个（<3 杀），笨办法：<...>
闸门3 付费信号：CPC $X，意图 <交易/商业/信息>，付费证据：<有/无，来源>
闸门4 护城河：<深度格式/合规本地化 具体是什么 / 无护城河，杀>
闸门5 获客可行性：头部产品 Search 占比 X%，<符合/不符合>约束
闸门6 量化验证：<转 research.md P2，见 <词根>-<日期>.md> / 未到这步
最终结论：GO / NO-GO / 待定，理由：<一句话>
```

被闸门 0–5 杀掉的方向同样要写一行进 `.rankup/rejected.md`（对象/类型/日期/理由/复活条件）——
**不能因为"很早就死了、没花配额"就不留痕**，`research.md` 阶段 0 的 grep 否决清单同样要能查到这些早期死亡的候选，
否则下一轮的自己会把闸门 0 就该杀掉的方向当新点子重新捡起来。

**2026-09-13 起这一步已自动化**：`scripts/select/gate-runner.mjs` 在某道闸门被 `--kill`、或七道闸门
全部 `--pass`（`passed_all`）时，会自动把上面这个模板追写进调用方 `--dir` 所在项目根的 `.rankup/decisions.md`；
闸门 0–5 判杀时同时追写 `.rankup/rejected.md` 一行（闸门 6 判杀已经转入 `research.md` 的完整量化流程，
不重复写 `rejected.md`）。按候选 slug 幂等，重复跑同一候选不产生重复行；追写失败会直接报错，
不会把本地判定悄悄记成"已完成"。不再需要人工按上面的模板手工补录——**只有在离线补记历史候选
（没有走 gate-runner 判定过程，只是事后把已有结论登记进来）时，才需要照这个模板手工写。**

`rejected.md` 那一行的"复活条件"栏由 `gate-runner.mjs gate <0-5> --kill` 的 `--revival <文本>` 参数写入——
不给就落一句诚实的占位（"未记录，需人工评估后补充"），不会替你瞎编一个复活条件。
