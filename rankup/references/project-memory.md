本文件定义网站项目内 `.rankup/` 的结构、初始化模板和读写规则。它保存项目事实、决策、证据与经验，使后续执行者可以先恢复上下文，再继续建设和增长工作。

## 核心原则：这是一部 Wiki，不是一本日志

`.rankup/` 里的大多数文件（`journal/` 除外）是**大家共同维护的一部 Wiki**，不是按时间顺序追加的流水账。这条原则解释了下面几乎所有规则为什么这样定，先立住它，再看细节。

- **日志回答「2026-08-22 发生了什么」**：已记录的判断原文不改写，按时间顺序读；逐步操作、命令输出这类流水按 [`maintenance.md`](maintenance.md) 压缩成结论加依据。`journal/` 属于这一类，仅此一类。
- **Wiki 回答「现在的事实是什么、为什么」**：原地持续修订，按主题读，**一个结论被推翻后，要在它最初出现的位置改写，而不是只在更晚的地方写一句反驳。**

这条原则要防的失效场景很具体：读者翻到一处措辞笃定的旧结论，照着做了决定，而真相是三份文件之后它已经被推翻——读者没有任何办法察觉。正确的处理方式是**原地修正**，不是在别处留一句矛盾的话:

1. 到结论最初写下的地方，把它改写成当前事实；
2. 给这条被修正的记录标注日期，写清楚“此前认为 X，YYYY-MM-DD 发现 Z，现改为 Y”；
3. 指向记录新推理的位置（决策编号、日志日期或主题文件路径），历史仍然可查，但正在被读的这一页不能说假话。

`decisions.md` 的 `superseded` 状态、`keywords.md` 的复查日期、下文的「时效契约」和「提升路径」都是这条原则的具体落地，不是独立规则。

## 目录结构

保持以下路径和职责稳定。每个文件后面是它回答的问题和明确不装什么——内容放错文件是这套体系最常见的真实故障：证据混进 `plan.md`、决策混进日志、一份还在变动的目标清单被当成历史记录锁死在某篇专题笔记里。

```text
.rankup/
├── INDEX.md
├── PROJECT.md
├── checks.md
├── architecture.md
├── infrastructure.md
├── integrations.md
├── secrets.md
├── skill-state.json
├── baseline.md
├── keywords.md
├── decisions.md
├── rejected.md
├── competitors.md      # 可选，仅非英语市场需要
├── research/
├── audit.md
├── plan.md
├── roadmap.md
├── iterations.md
├── experiments.md
├── releases.md
├── experience.md
├── scripts/
├── evidence/           # 脚本临时落盘目录；原始数据不常驻，结论进文档（收尾与提交由 rankup-clean.mjs 列待确认）
├── agentic/            # is-agentic 基线（scripts/review.mjs 检查）
├── tasks/              # 定时任务参数；一次性任务 brief 放 tasks/briefs/，收口后压缩
├── review-state.json   # sessions.mjs 的水位线，可选
├── journal/
└── topics/
```

目录里每个文件保留什么、什么内容该去哪、多大算超标，见下文[「目录规范」](#目录规范常驻文件保留什么去哪里多大)。

- `INDEX.md` —— 回答「现在该先读哪几份文件、项目走到哪一步了」。放导航、文件状态表、阶段与阻塞项。不装具体事实本身（事实在对应专题文件），不装历史变化过程（那是 `journal/`）。
- `PROJECT.md` —— 回答「这个项目是什么、为谁做、边界在哪」。放目标用户、定位、商业模式、目标与非目标。不装当前进度（那是 `plan.md`），不装做过的取舍权衡（那是 `decisions.md`）。
- `architecture.md` —— 回答「系统现在长什么样」。放应用、包、数据模型和服务边界的当前状态。不装“为什么这样设计”的推理过程（那是 `decisions.md`），不装施工细节和一次性排障（那是 `journal/`）。
- `infrastructure.md` —— 回答「线上跑在哪、绑定了什么资源」。放 Cloudflare 环境、非敏感资源标识、bindings 和域名的当前状态。不装密钥真实值或可还原真实值的片段（那是 `secrets.md` 的元数据契约），不装部署过程记录（那是 `releases.md`）。
- `integrations.md` —— **所有平台接入的唯一看板**。每项标 ✅（已接+证据+验证日期）/ ⬜（待做）/ ❌（不接+裁决依据），完成一项立刻打勾，和 backlink 台账同理。`rankup review` 会逐项线上实测验证（`curl` grep beacon / 后台查状态），不采信勾。新项目 `init` 时用完整平台清单初始化全部 ⬜，清单的一行一平台粒度与硬提醒见 [`discipline.md`](discipline.md) 十，不在本文件重复。不装接入过程的排障细节（那是 `journal/`）。
- `secrets.md` —— 回答「有哪些密钥、由谁管、什么时候轮换」。只保存密钥元数据，绝不保存真实值（见下文安全契约）。
- `skill-state.json` —— 回答「本地 Skill 版本是多少、上次检查更新是什么时候」。由版本检查脚本维护，不手工编辑事实性描述。
- `checks.md` —— 回答「每个环节的闸门过了没有、证据是什么、第几轮过的」。一个环节一段，每条标 ✅ / ⬜ / ⏸ / ❌ 加证据与日期，格式见 [`checklists.md`](checklists.md)。**它只存状态，判据在 Skill 侧**，两处不得各存一份。
- `baseline.md` —— 回答「技术、SEO、流量、转化、收入、成本现在处于什么水平」。每个数字必须带观察日期（见时效契约），不装目标值（目标在 `PROJECT.md` 的成功指标或 `plan.md`）。
- `keywords.md` —— 回答「做哪些词、每个词的 SERP 实况和复查日期是什么」。这是当前生效的目标清单，一旦改动必须联动检查引用它的文件（见写入与一致性规则）。不装选词过程的推演（那是 `journal/` 或提升后的 `topics/`）。
- `decisions.md` —— 回答「重要决定是什么、为什么这样定、什么条件下要重新评估」。每条决策必须有可判定的复查/证伪条件。不装尚未拍板的选项讨论（那还在 `journal/`）。
- `rejected.md` —— 回答「哪些词、方向、功能、渠道、域名已经被 pass 掉了、为什么、什么条件下才能重新考虑」。一行一个对象，专为**开工前 grep** 设计：任何一轮调研、迭代、功能规划开始前先在这里查一遍，命中的要么跳过并引用，要么按「复活条件」写明为什么这次可以重开。它存在的理由是一个真实故障形态：上一轮调研否决了某个词（意图撞词、量归了别的意思、折不成钱），下一轮换个人或换个会话又把它当新点子捡起来，重新实现一遍然后再踩同一个坑。`decisions.md` 的 `superseded` 记的是「决定如何演变」，这里记的是「什么不该再碰」，两者互相链接不互相替代。不装还没定论的候选（那在 `research/` 的报告里）。
- `competitors.md`（**可选**，只有做非英语市场才需要）—— 回答「这个语种/国家里，已经验证过的本地竞品长什么样」。持续累积、随时可改（区别于 `research/` 只增不改），每行带观察日期。12 字段：国家与语言 / 关键词（当地语言原词）/ 中文含义 / 搜索意图 / 竞品网站 / 页面类型 / Title 与 H1 / 高频相关词 / 页面模块 / 本地化特点 / 可参考之处 / 不足与机会。取法见 [`playbooks/research.md`「小语种候选词三关与本地竞品取词」](playbooks/research/p2-keyword-root.md#小语种候选词三关与本地竞品取词)。不存在不算缺文件，`scripts/review.mjs` 的必需/推荐清单都不含它。
- `research/` —— 回答「某个词根/方向那一轮调研到底查出了什么」。一次调研一份报告（`<词根>-<日期>.md`，固定八节：国家与语种 / SERP 页面类型 / 扩树 / 量·KD·CPC / 筛子 / 社区验证 / 意图核验 / 折成钱与裁决），报告开头必须有「已否决对照」段说明查过 `rejected.md`。历史报告只增不改；结论提升到 `keywords.md`（做）或 `rejected.md`（不做）。功能与实现层面的调研（该不该做某个功能、选哪个库、竞品怎么实现）同样落这里，文件名用 `feature-<名>-<日期>.md`。
- `audit.md` —— 回答「发现了什么问题、现在是什么状态」。放问题、证据、严重度、状态和复验结果，需要随复验更新，不是一次性清单。不装长期方向（那是 `roadmap.md`）。
- `plan.md` —— 回答「这一轮要做什么、验收标准是什么、卡在哪」。放当前优先级、负责人、状态、验收标准和阻塞项，是易变的活文档，随进度原地更新，不追加历史版本。不装已经做完并稳定下来的结论（那应提升进 `topics/` 或 `decisions.md`）。
- `roadmap.md` —— 回答「长期往哪走、分几个阶段、每阶段怎么算过关或放弃」。每个阶段写清进入条件、判定条件与放弃条件，跨会话可续，不随单轮任务改写。不装单轮执行细节（那是 `iterations.md`）。
- `iterations.md` —— 回答「上一轮做了什么、判据是什么、结果如何、下一轮唯一改进是什么」。每轮迭代一段，失败轮次必须记录并写明被证伪的假设，否则同一个错误会被重复执行。不装长期方向（那是 `roadmap.md`）。
- `experience.md` —— 回答「本项目积累的、可在本项目内复用的结论是什么」。保留证据出处与具体数字，是 `topics/` 提升前的沉淀层（部分团队直接把结论按主题拆进 `topics/`，两者并存时以主题拆分为准，`experience.md` 退化为索引）。
  **每条必须以 `- **[YYYY-MM-DD] 标题**` 起头**，正文缩进两格接在下面：

  ```markdown
  - **[2026-01-15] 一句话说清这条结论**

    正文。保留数字与证据出处。
  ```

  这不是排版偏好，是 `scripts/review.mjs` 的**切分依据**。用 `## 标题` 分条会让它读出
  「条目总数：0」，于是重复检测与回流候选**从建库起就没工作过**，而报告看起来一切正常。
  这是本协议里最容易发生的静默失效，实测踩到过一次：一个已积累 12 条结论的库长期被报成 0 条。
- `scripts/` —— 回答「哪些操作已经固化成脚本、怎么调」。放可复用操作脚本，尤其是浏览器操作。不装脚本产出的数据本身（数据进对应专题文件）。
- `experiments.md` —— 回答「做过什么实验、指标和时间窗是什么、结论是什么」。放假设、变更、指标、时间窗和结论。不装尚未设计好对照的想法（那还在 `journal/`）。
- `releases.md` —— 回答「上线了什么、验证过没有、能不能回滚」。放发布版本、环境、验证、监控和回滚信息，每次发布一条记录，不回改历史条目（发布记录本身是准日志性质，但仍需与 `infrastructure.md` 等当前状态文件保持一致）。
- `journal/` —— 回答「某一天具体发生了什么」。这是全目录里唯一真正的日志：按日期记录，已写下的判断即使后来被推翻也不改写原文，只在推翻它的地方（`decisions.md` 或 `topics/`）反向链接回来；逐步操作、命令输出、一次性 brief 这类流水按 [`maintenance.md`](maintenance.md)「三」压缩成结论加依据（2026-09-30 统一口径，此前写作「只增不改、永久保留」）。不装应当长期有效的结论（那些要提升出去，见下文提升路径）。
- `topics/` —— 回答「关于某个主题，现在整理后的、当前有效的知识是什么」。经过整理、可在本项目复用的专题经验，按主题组织、持续修订，是 Wiki 属性最强的目录。不装带时间线性质的叙述（那是 `journal/` 的事），不装还没经过至少一次验证的猜测。

## 每次任务的读取顺序

1. 读取 `.rankup/INDEX.md`，确认项目地图、当前阶段、最近变化和相关文件。
2. 读取 `.rankup/skill-state.json`，确认 Rankup 版本和更新检查状态。
3. 读取 `.rankup/PROJECT.md`，恢复目标、约束和非目标。
4. 只读取当前任务需要的专题文件；不要无差别加载整个目录。
5. **本轮要碰的每个对象（词、方向、功能、渠道、域名）先 `grep -i` 一遍 `rejected.md`**，再看 `research/` 有没有同对象的旧报告。命中否决清单的只有两种处置：跳过并引用那一行，或写明「复活：<复活条件> 已满足，证据 <…>」再继续。没有第三种，尤其不许「没注意到所以重做了一遍」。
6. 在采取行动前，把记录与当前代码、Git 历史和适用的线上提供方重新核对，并对每条会变化的事实按下文时效契约打折扣。

记录是上下文，不是永远正确的事实。涉及部署、资源、索引、支付或外部账户时，必须按任务范围核对代码与 Git，并检查 Cloudflare、GSC、Stripe 或其他实际系统。无法访问某个系统时，明确标记“未实时验证”，不要把旧记录描述为当前状态。

## 时效契约：Wiki 会静默腐烂，必须显式标注

任何可能变化的事实性陈述——排名、索引数量、竞品位置、当前上线的 URL 集合、流量数字——**必须带上被观察到的日期**，读者据此打折扣，不能把它当常量看待。写“已被 Google 索引”而不写日期，等同于宣称这件事永远成立，而这几乎从不成立。

- 格式：陈述 + 观察日期，例如「三个页面均已被 Google 索引（2026-08-10 GSC 核实）」，而不是「三个页面均已被 Google 索引」。
- **状态可以倒退，必须允许并记录倒退**。真实发生过的案例：项目记录“这三个页面都已被 Google 索引”，几天后其中两个掉出了索引，而笔记仍然停留在现在时态，读它的人会误以为三个都还在。索引、排名、集成状态这类事实不是单调递增的，每次核对都要**如实覆盖**上一次的状态，不能只在变好时更新。
- 涉及外部系统（GSC、Stripe、Cloudflare、竞品页面）的陈述，核对方式本身也要留痕——“未实时验证”和“已于 <日期> 用 <方式> 验证”是两种不同强度的事实，不要合并成一种语气。
- `baseline.md`、`keywords.md`、`integrations.md`、`infrastructure.md` 是时效契约覆盖面最大的四个文件，每次任务涉及它们时，先看日期是否还在可信区间内，过期的要么重新核实，要么明确标注为待核实,不要默认沿用。

## 提升路径：journal → topics → decisions

这是防止 Wiki 淤积成流水账的机制。信息只能沿一个方向变得更“正式”，越往后越难改动，也越有约束力：

1. **`journal/`（原始、带日期）**：任何观察、操作、临时判断先落在这里。默认起点，不需要门槛。
2. **`topics/`（整理、当前有效）**：一条结论从 `journal/` 提升到这里，要求满足下列任一条件——
   - 同类观察在不同日期或不同场景下重复出现过至少一次，不是单次巧合；
   - 结论对后续任务有直接指导作用（不只是“发生过”，而是“下次可以照此判断”）；
   - 结论已经和当前代码/线上状态核对过，不是纯推测。
   提升时**保留原始日志的来源链接**（日期 + 相对路径），日志本身不删除、不改写，Wiki 页面负责当下正确，日志页面负责历史可查。
3. **`decisions.md`（裁决，带复查/证伪条件）**：一条整理好的知识如果对应一次需要被后来者遵守、且可能需要被推翻的具体选择（技术选型、范围取舍、放弃某个方向），进一步提升为决策条目，必须写清备选方案、证据和复查/证伪条件——没有可判定的证伪条件，就还不是决策，只是主题笔记。

**什么不该提升**：只发生过一次、没有指导后续任务的操作细节（例如某次部署的具体报错和修复步骤），留在 `journal/` 就够，不要为了“显得完整”硬凑成主题文件。判据始终是「下次遇到同类问题能否少走一遍」——不能，就不提升。

## 清理协议：Rankup 只留长远规划和当前进展

## 接力协议：任务随时可能中断，新会话必须立即接上

Claude Code 的 prompt cache 最长 1 小时（超额后降到 5 分钟），会话也可能因为额度、崩溃、用户关窗口随时结束。**不能指望收尾时再写**：任务可能根本走不到收尾。所以 `INDEX.md` 顶部四个字段加「## 接力」一节，是跨会话唯一可靠的上下文。

**什么时候写（硬性）**
1. 有状态变化（改文件、派任务、做出结论）前先写一次；纯只读问答免写：把本轮任务、验收条件、计划的第一步写进「接力」。
2. 每完成一个里程碑就覆盖更新（一个页面上线、一批词调研完、一次部署、派出或收回一个后台任务、做出一个决定），不攒到最后。
3. 派出后台任务（fleet/Codex/Gemini）时立刻记下任务名和结果文件路径，否则新会话不知道有东西在跑。
4. 任务结束（完成、失败、被叫停、等用户决定）时，按 [`maintenance.md`](maintenance.md)「一」选择轻量路径或「二、收尾维护」五步，最后覆盖一次接力，并同步 `plan.md`、根层 `.rankup/portfolio.md` 与 `projects.json`（校验规则见同文件「四」第 8 条）。
5. 写完 `grep -n "下一条要执行的动作" .rankup/INDEX.md` 确认已落盘；「接力」只写当前状态，覆盖旧内容，历史进 `journal/`。

无 `.rankup/` 时，以上内容写进项目根 `HANDOFF.md`（或已有进度文件），同样实时覆盖与收尾清理，不强制完整 init。

**新会话怎么接（用户说「继续」「/rankup 继续接下来的任务工作」时）**
1. 定位项目：当前目录有 `.rankup/` 就用它；在工作区根目录时读根层 `.rankup/portfolio.md` 与 `projects.json`，优先用 `last_activity` 定位最新且接力未完成的项目；缺该字段再读候选项目 `INDEX.md` 的「最近更新」，只有一个候选就直接进，多个才列出来让用户选。
2. 读 `INDEX.md` 顶部字段和「接力」一节（无 `.rankup/` 则读项目根 `HANDOFF.md` 或已有进度文件）；有后台任务的先查结果文件是否已产出；有未提交改动的先 `git status` 核对。
3. 按启动协议第 2 步三方对账（doctor 例外见维护「六」），确认接力记录没过期，然后直接执行「下一条要执行的动作」，不再问用户要不要继续。
4. 接力记录缺失或和现实对不上，先按 git 日志、`journal/` 最新一篇、`plan.md` 还原并回写，再继续。

### 压缩/换会话前的接力核对

上下文将压缩、切换会话或阶段换乘前，按现有模板核对目标与验收、本次限制及用户新纠正的指针、实际产物、运行中任务和下一动作。明细留计划或报告，接力只存事实与证据指针，不复制长工具输出或自行编辑运行平台的 API 历史；仅写获准位置。新会话先恢复限制并核对必要产物再执行，完成标志是可直接续做，证据与授权不靠摘要猜测。

## `INDEX.md`：任何人一分钟内看懂项目现在在哪

这是整个协议里对“任何人都能接手”这个目标最直接的落地点。`INDEX.md` 必须让一个完全没参与过此前工作的人，在读完它、不需要打开第二份文件的情况下，回答四个问题：

1. **现在处于生命周期哪个阶段**（对照 `lifecycle.md` 的阶段编号）；
2. **上一个通过的关卡是什么**（哪个阶段的判定条件已经满足，何时满足的）；
3. **下一步动作是什么**（具体到可以直接开始做，不是一句“继续推进”）；
4. **当前被什么卡住**（阻塞项、缺的权限或决定，没有阻塞就明确写“无阻塞”）。

初始化模板里的 `INDEX.md` 结构（见下文）已经把这四项做成固定字段，不要省略任何一项——省略掉的那一项，就是下一个接手人要重新调查一遍的成本。

**`~/.agent-reports` 是临时目录（CRITICAL）**：`~/.agent-reports/` 随时可能被清空，不是持久存储。任务产出的分析报告、执行结果等需要跨会话复用的文档，必须在任务收尾时迁移到项目 `.rankup/reports/`（或 `research/`），并更新引用指针；brief、body、raw data 等过程文件可以留在原处自然清理。`cost-optimization-plan.md` 等汇总文件里引用 `~/.agent-reports` 路径的，一律改为 `.rankup/` 内的相对路径。

**工作区根层**：`.rankup/` 可保留 `README.md`（工作区说明）、`portfolio.md`（项目总表）、`projects.json`（登记数据）与 `log.md`（根层历史记录，按 journal 规则压缩）。存在 `portfolio.md` / `projects.json`，或诊断参数指明项目根等于工作区根时按根层识别；普通项目根本身的文件不属于 `.rankup/` 扫描范围。`archive/` 是历史原文，`backlink/` 是脚本产物，均不按常驻文件体积检查。`tasks/briefs/` 收口后只留结论与报告指针。

## `secrets.md` 安全契约

`secrets.md` 只能使用以下八列，列名和顺序保持一致：

```markdown
# 密钥登记

| name | purpose | environment | provider/storage location | owner | access status | rotated at | next rotation |
|---|---|---|---|---|---|---|---|
| <非敏感名称> | <用途> | preview/staging/production | <Worker Secrets、Secrets Store、CI 或提供方控制台> | <负责人或团队> | available/restricted/rotation-needed | <日期或 never> | <日期或待定> |
```

即使 `.rankup/` 没有提交 Git，也禁止写入：

- 密钥真实值或可以还原真实值的片段；
- 访问令牌、会话令牌、OAuth 凭据和授权头；
- 私钥、助记词、证书私钥和签名材料；
- Webhook 签名密钥；
- 密码、恢复码和一次性验证码；
- 完整支付卡信息、银行信息或其他支付敏感数据；
- 不必要的个人身份信息、联系方式或可识别用户的数据；
- 生产数据样本、日志或命令输出中夹带的上述内容。

真实值只进入 Cloudflare Worker Secrets、Cloudflare Secrets Store、Stripe Dashboard、受控 CI secrets 或用户明确选择的密钥管理系统。命令输出和测试夹具也不得包含真实值。发现泄漏时停止传播，按提供方流程撤销或轮换，并只在项目记忆中记录事件、影响和轮换状态。

## 写入与一致性规则

- 只记录经过观察或验证的事实；推测必须标记为“假设”并附复查条件。
- 每次实质变更都更新最小必要文件，并给记录加日期、证据和关联路径。
- **改动一份被别处引用的清单之前，先在仓库里搜谁在引用它，尤其是成功判定和放弃条件。** 真实发生过的事故：一份关键词目标清单从 8 个词改成 4 个，但另外三份文件的通过/放弃判据仍然写死“这 8 个词”——结果是一个已被剔除的词自己涨进前 20 名，会被误判成本轮任务成功。改动前至少 grep 一遍清单标识符（词表名、阶段名、数量），逐一确认每个引用处是否需要同步改写。
- 外部状态变化时，搜索并更新所有过时交叉引用，而不只修改首次发现的文件。例如生产域名、Worker 名称、D1 migration、Stripe 模式、发布 SHA 或索引状态变化后，同时检查 `INDEX.md`、`infrastructure.md`、`integrations.md`、`plan.md`、`releases.md`、相关日志和主题文件。
- **改旧数字时用显式否定句，不要默默替换。** 例如「不是 8 个词——旧表述已作废，现在是 4 个词，见 DEC-20260822-01」，而不是直接把“8”改成“4”不留痕迹。持有旧引用或旧记忆的人读到显式否定句才会意识到自己手里的信息已经过时；静默替换只对第一次读到新版本的人有效，对所有凭记忆或旧笔记行动的人无效。
- 把被取代的决定标记为 `superseded`，保留历史依据，不静默改写过去——这条只对 `decisions.md` 生效，`journal/` 之外的其余文件仍应遵循「Wiki 原则」原地修正，两者不矛盾：`decisions.md` 记录“决定本身如何演变”，其余文件记录“当前事实是什么”。
- `INDEX.md` 的文件状态和“最近变化”必须与本次写入同步，四个导航字段（阶段/上一关卡/下一步/阻塞）尤其不能漏更。
- 日志是时间线，主题文件是当前整理后的知识；定期把稳定结论提升到 `topics/`（标准见上文「提升路径」），并在日志保留来源链接。
- 只有经多次验证、与具体项目无关且可跨项目复用的经验，才候选回流 Rankup Skill；项目秘密、账户标识和用户数据永不回流。回流时只带走剥离站点后仍成立的规则，本项目私有站名、域名、流量数字与证据出处留在 `experience.md`；公开供应商地址与必要公开来源可保留。

## 沉淀义务

写回 `.rankup/` 的义务只取决于项目里有没有这个目录，与本轮是否调用了 Rankup Skill 无关。

- 该项目中**任何**任务完成后都要判断有无沉淀（轻量路径见维护「一」），不限于 SEO——功能开发、重构、排障、发版、依赖升级同样适用。
- 判据是“下次遇到同类问题能否少走一遍”。能，就写；不能，就不写，避免堆流水账。
- 用户没有显式要求也要写。写完在回复里提一句写了什么即可，不必请示。
- 长期方向进 `roadmap.md`，单轮结果进 `iterations.md`，可复用结论进 `experience.md` 或提升进 `topics/`，一次性排障过程进 `journal/`。
- 调研报告（词根、方向、功能、竞品实现）进 `research/`，一次一份、只增不改；本轮 pass 掉的每个对象带理由与复活条件进 `rejected.md`；做的词进 `keywords.md`。**沉淀的范围是全部**：调研背景、每次优化、功能调研、功能实现、关键词检索，凡是「下次会想知道当时为什么这么定」的都写。规则要活：写的是判据与理由，不是禁令——理由在，后来者才能判断条件变没变。

## 三层归属与用户全局层（资产位置）

此表只列资产位置与 Git 登记；经验归属统一按 [maintenance.md「七」](maintenance.md#七经验分层与回流四层归属唯一判定表) 的四层判定，不另立分类规则。

| 层 | 位置 | 放什么 | 进 Git 吗 |
|---|---|---|---|
| Skill | 本 Skill 仓库 | 剥离站点后仍成立的通用方法与规则 | 是，且开源 |
| 项目 | `<project>/.rankup/` | 本站的事实、数字、裁决、脚本、登录态与凭据存放位置 | 进该项目仓库 |
| 本机 | Skill 目录下的 `registry.md` | 跨项目资产索引（项目名、路径、脚本清单） | **否**，gitignore + 构建断言双保险 |
| 用户全局 | `~/.rankup/`（`RANKUP_HOME` 可覆盖）：`preferences.md`、`lessons.md`、`upstream-candidates.md`、`config.json` | 只对这个用户或这台机器成立的 rankup 规则、回流候选、扫描根配置 | **否**，不在任何仓库里；Skill 目录里不得出现这几个文件（validate 断言） |

经验该写进哪一层，按 [`maintenance.md`「七」](maintenance.md#七经验分层与回流四层归属唯一判定表) 的判定问题序列走。

登记表由 `rankup/scripts/registry.mjs scan` 扫描生成，不手工维护。它含项目名与绝对路径，
描述的是这台机器上项目之间的关系，因此文件虽然放在 Skill 目录里，却绝不进 Git：
`rankup/.gitignore` 排除它，`validate-rankup.mjs` 再断言它未被追踪，`git add -f` 也会当场构建失败。

## 可复用操作脚本

任何需要第二次执行的操作，第一次跑通时就固化成脚本，不允许下次重新摸索。浏览器操作是最主要的适用对象。

- **判定**：满足“会再做一次”或“换个站/换个词就要重跑”即为可复用操作；一次性排查不适用。
- **命名与位置**：`.rankup/scripts/<动词-对象>.mjs`，例如 `gsc-switch-property.mjs`、`gsc-export-queries.mjs`、`serp-top10.mjs`。
- **参数化**：property、日期范围、关键词、国家等一律作为参数，不得写死某一次的具体值。缺参数时报出人话错误，不要静默用默认值。
- **登记**：在 `INDEX.md` 记一行——用途、参数、依赖的登录态、已验证日期。
- **维护**：失败时修脚本，不是绕过它手工再点一遍。页面改版是正常损耗；修完更新已验证日期，并把失败原因写进脚本头部注释。
- **归属**：脚本连同它依赖的登录态、property ID 与账号配置都只属于本目录，永不回流 Skill。
