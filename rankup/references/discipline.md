## 一、执行纪律：全权委托

**在用户当前任务范围内全权执行，沿用已有授权；调用技能不扩大任务范围。用户明确的先审批、只规划、不提交等限制始终有效。**

### 任务验收与探索终点

多阶段调研、狭窄修复或“优化”任务开工时，从 brief 提取问题、允许动作、交付与足够的完成证据；可推断的直接采用默认值。每轮探索对应未解决问题，复用已有有效证据；新机会只记候选。达到本次验收后收口；新反证或同根因验收失败继续调查。交付覆盖问题，无关旧待办不加入完成条件，未验证项明确标出。

### 分工、取数编排、派单与模型档位：按 `/agent-fleet`

主 Agent 与子 Agent 怎么分、独立读数怎么并行、派单带什么、收回怎么核、派给哪个模型与失败后怎么换手，一律按 `/agent-fleet` 当前规则与使用者的 Agent 全局规则；本 Skill 不另立一套，避免两处规则各自过期。只回一句「已启动」不算交付。

### 全量执行，不问不等

| 规则 | 为什么 | 反面教材 |
|---|---|---|
| 当前目标、必要依赖、本次引入的问题和阻碍验收的同根因问题——**全部做完**；无关旧待办与新机会只记录 | 这个 Skill 的用户不是在试探，是在执行；问一遍等于白白多一轮对话 | 「还有几项待办未处理，需要我继续处理吗？」 |
| **不重复索要已有授权**。普通细节自主判断，范围内问题直接修；必需信息无法获取或推断时才询问 | 请示的成本是用户切回来看、理解、回复、你再继续的整条链路 | 「发现 key 是错的，要不要我修？」 |
| 必要依赖不截断：沿当前目标的因果链完成；无关任务不加入完成条件，调查任务以调查结果为终点 | 截断让用户变成人肉任务队列 | 修了 key，发现脚本有 bug，汇报 bug 然后等用户说「修一下」 |

### 测试身份与登录通路

需要登录态的验收、E2E 或线上测试，开工先读项目索引的「项目概要」、派单包（dispatch-kit）与项目记忆；已有测试身份就直接用，不向用户重复索要。用户在对话里新给的测试身份，立即将身份标识与受控存储位置写入项目索引「项目概要」、派单包与用户记忆，之后不再问；密码、验证码、token 等秘密只经受控存储与进程通道使用，不写入这些记录。

缺登录通道不等于缺输入：在已有授权与真实访问控制内，先穷尽项目取 token 脚本及其依赖配置、已授权云账号与跳板或 SSM 通路、项目文档的 admin 入口说明、此前报告里已验证的做法；能修复的通路自行打通，将命令与依赖位置（不含秘密）写回项目派单包。只有确实需要用户本人才能取得的新权限，例如本人接收的短信验证码、本人才能开通的权益，才作为「需要用户」上报，写明确切缺口与最小所需输入；只阻塞依赖该权限的步骤，其余继续。

测试身份下的验收默认只动该账号自己拥有的测试空间与测试页面，用后清理并读回；不购买、不升级套餐、不绕过产品权益限制。权益限制属于边界，不是询问用户的理由：受限环节如实标未验，换该账号下满足条件的资源（例如有对应权益的空间）继续；没有合适资源则记录未验范围。

〔用户定〕复用测试身份可以减少重复授权，并保持验收在既有访问边界内。

### 范围扩张需要用户圈定，不算「请示」

全权委托覆盖的是「把已经定好范围的任务执行到底」，不覆盖「范围本身要不要扩大到包含某个新对象」。调研/筛选判定某个候选「技术上站得住」，只说明它没有硬伤、值得摆上桌，不代表它已经进了这一轮要执行的范围——这是两个独立的判断，不能把前者当成后者的默认结果。

| 规则 | 为什么 | 反面教材 |
|---|---|---|
| 调研/筛选得出的候选清单，只代表「技术上没问题、值得摆上桌」，不等于「这一轮该执行」；凡是会产生不可逆公开可见后果的批量对外投递/发布类任务，候选清单出来后先完整摆给用户一遍，等用户明确圈定这一轮实际要执行的子集，再进入执行阶段——这一步是在确认范围边界，不是「问要不要继续」，不违反全权委托 | 技术判定覆盖的是存活状态、内容完整度、是否占位这类客观维度，覆盖不到用户自己的曝光意愿与节奏考量，这类决定只有用户能给；全权委托授权的是「执行」，不是替用户做「范围」决策 | 候选清单判定完「技术上可以对外提交」，不等用户圈定子集就直接把候选逐个排进执行队列 |

### 人机验证：自动化到最后一步，只把那一下点击留给用户

| 规则 | 为什么 | 反面教材 |
|---|---|---|
| 遇到 CAPTCHA / 短信验证码等无法自动化的节点，**前面所有能自动完成的步骤全部做完**（表单填好、页面打开好） | 用户不该重复做机器能做的事；一个 CAPTCHA 不是放弃整条流程的理由 | 把 Naver 注册整套 SOP 甩给用户 |
| **必须用用户的浏览器打开到那个页面**（`opencli`，不是 Claude in Chrome 一类内置浏览器工具——理由见五「这个『用户的浏览器』必须由 opencli 驱动」），不是给一个 URL | 用户看到的应该是已填好的表单，只差点一下 | 「请前往某某网址，输入某某，然后点击某某」 |
| 做完之后**明确说现在浏览器里哪个标签页、要点什么** | 用户切到浏览器应一眼知道该干什么 | 「已打开页面，请完成验证」 |

适用于所有平台：Cloudflare Turnstile、Google reCAPTCHA、任何短信验证码、任何需要人眼识别的步骤。
目标是把用户的操作量从「一整套 SOP」降到「一次点击」。

### 收尾不留尾巴

做完之后的产出是**一段简报**，不是待办清单：做了什么（每项一行）、验证结果（通过/失败）、
确实无法自动完成的事项（写清为什么不能自动做，**以及你已经自动化到了哪一步**）。
「还有 X 没做，要不要做？」这种结尾**禁止出现**。

简报样例：**结果**：本次文档修订已落盘。**证据**：结构与断链检查通过，详情见报告。**阻塞**：无。行为效果未验证，后续评测另按任务范围执行。报告长度按任务复杂度与用户上限校准，必要来源保留。

## 二、红线：先查脚本清单，禁止重造轮子

**凡是清单里已有的能力，一律调用现成脚本；不准在对话里现写一段等价实现，也不准手工点一遍界面。**
现写的实现每次形状都不一样，结果不可比、踩过的坑要重踩、上下文白烧，下次换个报表还得再写一遍。
**脚本坏了就修脚本**（改完更新头部的已验证日期），不要绕过它。

判定顺序，从上往下，命中即停：

1. 本 Skill 与兄弟 Skill 的脚本（底账在 [`capability-map.md`](capability-map.md)）；
2. 跨项目资产登记表 `registry.md`（别的项目已写好的，直接去那个路径取）；
3. 当前项目的 `<project>/.rankup/scripts/`；
4. 都没有 → 才新写，写完立刻按 [`maintenance.md`「五」第 1 条](maintenance.md#五维护-skill-源码rankup-本身)「可复用操作落成脚本」固化并登记。

### 取数的强制优先级（禁止跳级）

公开 SERP 的顺序只按 [SERP 取数路线](seo-serp.md#serp-取数路线)，不套用以下阶梯。

1. **现有脚本**（`node scripts/xxx.mjs`）；
2. **HTTP/REST API**（`fetch` / `curl`）→ 用完固化成脚本；
3. **用户浏览器 + 现有自动化脚本**（底层走 OpenCLI）→ 没有 API 且需要登录态时；
4. **用户浏览器 + 手动 OpenCLI** → 一次性探路或脚本不覆盖时。

每一级向下的**唯一理由**是「上一级确实不存在」，不是「我对下一级更熟」。
沙箱浏览器不作为本机选项——它没有登录态，用它查需要登录的面板必然拿到错误数据。

**Cloudflare 特别提示**：Wrangler CLI 认 `CLOUDFLARE_EMAIL` + `CLOUDFLARE_API_KEY`（Global Key）
或 `CLOUDFLARE_API_TOKEN`（scoped token）环境变量，**配好后不需要 `wrangler login`**。
段 5 密集操作 CF（DNS、Email Routing、zone 设置），先把环境变量配好（Skill `.env` 或 shell 环境变量，见本文十一），
后面 wrangler 命令和 `curl` API 调用都直接用。Dashboard 上某些开关偶尔点击无响应
（实测 Email Routing 启用开关），此时 API 能立刻生效——遇到 Dashboard 不动别反复点，
直接走 API。【实测 2026-09-03】

**这个阶梯管「取数」，不替代「亲眼看」。** 任何调研在动用任何一级之前，先去 Google、Bing 与目标市场的
本地引擎把词搜一遍，记第一页的页面类型——数据平台给的是模型外推，首页是搜索引擎此刻真正端给用户的东西。
公开 SERP 的通道见 [SERP 取数路线](seo-serp.md#serp-取数路线)，并显式指定地区与语言。

### 抓后台数据的顺序（曾经写反过）

「抓一下后台数据」「导出这个报表」「这站没有 API」——**先查 [`provider-capabilities.md`](provider-capabilities.md)
有没有现成脚本，有就直接跑（`backlink/scripts/*`）；没有才加载 `backlink` 读它的 `harvest.md`**
（虚拟滚动、节流、静默丢行的陷阱全在那）。旧版主文件有两处写成「一律先加载 backlink」，
与取数优先级第 1 级冲突，已统一为「脚本优先」。

### 调研的验收单不是入口

`research-checklist.md` 是**跑完之后的验收单**，不是执行顺序，也不是入口。入口是
[`playbooks/research.md`](playbooks/research.md)。旧版主文件的两张路由表一处说「验收单」、一处说「入口，逐项走完」，
拿验收单当流水线跑会把 9 节清单串行走一遍而不是按 playbook 并行派活。

## 三、配额前置检查：花配额之前的第一个动作

**凡是有配额的数据源，开工的第一个动作是问自己在哪一档，不是查第一个词。**

真实事故（2026-08-22）：整场关键词调研按「匿名 10 次/日」规划，省着用，少测 4 个词，报告写成
「配额耗尽，无法验证」——账号其实是 VIP 500/日，当天只用了 66 次。没人问过档位，文档里的默认值被当成了事实。

| 数据源 | 档位怎么看 | 为什么这么定 |
|---|---|---|
| 哥飞工具箱 | 按[官方 Skill 入口](seo-webcafe.md)读取实时工具目录、价格、余额与用量 | 开放接口积分与网站赠送配额分开，以当前实际读数规划，不把旧默认档位当事实 |
| Similarweb / Semrush | 档位与到期日在面板启动时打印一次；**会话复用会跳过启动，读数不再刷新** | 两站已收敛到固定会话名（`semrush-nav` / `similarweb-nav`），复用是常态，所以开工那一次读数往往是全程唯一的一次，整场调研的规模要在开工时定死 |

## 四、脚本没有登录态而用户浏览器有：把请求发进浏览器，不要抠 cookie

httpOnly 会话**故意**不让 JS 读到，OpenCLI 也没有导出 cookie 的命令。正确解法不是取出凭据，
而是**把调用挪到已登录的页面里执行**——浏览器自动带会话，凭据全程不离开浏览器，不写 `.env`、不进日志、不进 git。

```bash
S="data-read"          # Bash tool 里用描述性常量，不要用 $$（每次调用 PID 都变）
opencli browser "$S" open "<需登录的数据页>"
opencli browser "$S" eval '(async()=>{ /* fetch(..., {credentials:"include"}) */ })()'
```

浏览器调用写法按 `opencli` Skill；哥飞调用入口见 [`seo-webcafe.md`](seo-webcafe.md)。**eval 体一律包 IIFE**——本环境 eval 上下文跨调用持续，
重复声明会抛错且那次调用根本没执行。

**哥飞工具取数**：加载[官方 `gefei` Skill](seo-webcafe.md)及对应专用 Skill，鉴权、工具与配额口径依官方当前说明执行；官方已覆盖的用途不要回退旧网络端点；官方无等价能力且仍保留的独有用途与社区原文入口见 `seo-webcafe.md` / `webcafe-forum.md`。本地 `money` / `kgr` / `string` / `email` 计算仍可复用，不代表旧网络路径恢复。

## 七、兄弟 Skill：本机装着几十个，能用的只有一小半

取舍、缺 Skill 的处置与同名陷阱全文在 [`skill-ecosystem.md`](skill-ecosystem.md)（兄弟 Skill 路由的唯一源）。找能力的顺序：[`capability-map.md`](capability-map.md) → `skill-ecosystem.md` → 最后才用 find-skills。**已点名的兄弟 Skill 本机没装 → 用 `find-skills` 装上再继续，不跳过、不现写替代。**

## 九、静默收尾动作：焊进命令，不要交给人记

**判据一句话：「漏掉这一步，会有什么东西变红吗？」答案是「不会」，那它就不该由人来记。**

改完代码准备出荷时，凡是「主要工作做完之后还必须做、但漏了不会有任何报错」的动作
（推送索引、清 CDN 缓存、打版本标签、发 webhook、重新抓 OG 图），**必须在同一个任务里焊进出荷命令**，
不允许以「记得跑一下 xxx」的形式交付。危险不在难，在**失败是静默的**：构建绿、测试绿、页面 200，没有任何信号提示你漏了。

正确形态三条（脚本进项目仓库 / 配置单一事实源 + 断言挂 `test` / 焊进 ship 后段）写在
[`search-platforms.md`](search-platforms.md)「挂进发布流程」——那边是权威，动手前去读那一节。
出荷前自查：**这次改动新增或修改了线上可访问的 URL 吗？** 是 → 出荷命令里必须含索引推送。

## 十二、完成标准

一次 `rankup` 工作只有同时满足以下条件才算完成：

1. 用户要求的产出已经存在。
2. 相关类型检查、测试、构建或迁移验证通过。
3. 若涉及发布，真实线上目标和关键路径已验证；上传成功或 Worker Ready 不能单独证明完成。若本轮初始化了绿地项目，**远端私有仓库必须存在且当前状态已推送**。
4. **本段 [`checklists.md`](checklists.md) 的 check 全部过闸**，每一项都在 `.rankup/checks.md` 记了证据；做不了的标 ⏸ 并写明原因。
5. 相关 `.rankup/` 文件已更新，过时的交叉引用已一并修正。
6. 说明完成内容、验证证据、仍存在的风险和需要用户处理的外部事项。
7. 本次必需子任务已交付并消化；一般阻塞只挡依赖部分，其他获授权工作继续推进；外部模型失败仍按上文停止规则执行。

## 十六、组件库红线（段 3 / 段 4）：UI 只准来自组件库，不许自己造控件

用户最常见的开口方式是「做个功能吧」「做个内页吧」，然后直接进开发。这时第一条约束不是 SEO，是 UI 从哪来：
项目是用 shadcn 的命令行初始化的，`components/ui/` 里已经有一整套组件，**任何功能、任何页面的控件一律从这里取**。

| 规则 | 为什么 | 反面教材 |
|---|---|---|
| 先 `ls components/ui/` 看有没有；有就用，没有就 `pnpm dlx shadcn@latest add <组件>`；shadcn 没有的装同一生态（Radix / React 生态里带可访问性的现成包），装完再用 | 组件库带着键盘导航、焦点管理、暗色模式、ARIA 和统一视觉，手写一个下拉框这些全丢，且每个站各写一遍没人维护 | 用 `<div onClick>` 拼一个下拉菜单；用绝对定位 `<div>` 当弹窗；自己写日期选择器 |
| **禁止手写**：下拉框、弹窗 / Dialog / Sheet、日期选择、表格分页、Toast、Tabs、Tooltip、Command 面板这类基础控件 | 这些正是最容易「看着能用、键盘和读屏全坏」的一类，也是 Lighthouse 可访问性分和 GEO 就绪度掉分的常见来源 | 「组件库那个不好改样式，我自己写一个」——改样式走 className 与 variants，不走重写 |
| 判据：在业务目录 `grep -rn 'role="dialog"\|role="listbox"\|role="combobox"\|<select' apps/`，命中的每一处都要能指出来自 `components/ui/` 哪个文件或哪个已安装的包；指不出来的就是手写，打回 | 让「有没有手写」变成可 grep 的事实，不靠自觉 | 代码评审时说「应该都是组件库的」 |
| 这条与「不重复造轮子」（段 3）是同一条纪律在 UI 层的落地，闸门在 `checklists.md` 段 3「UI 只来自组件库」，步骤 check 在 `references/lifecycle/stage-3-scaffold.md` 3.3 | 一处判据两处指路，不各存一份 | — |

## 十八、ID / token / 密钥等标识符禁止从截图或记忆中抄录

复制任何平台分配的标识符（Measurement ID、Project ID、Tracking Code、API key、
CNAME 值、TXT 记录值等）时，**必须从页面元素直接获取文本或点击平台的复制按钮**。
禁止从截图 OCR、从上一次对话的记忆、或从人工转录中抄录。

| 规则 | 为什么 | 反面教材 |
|---|---|---|
| 获取 ID 的唯一合法来源：页面 DOM 里的文本节点（`read_page` / `get_page_text` / `javascript_tool` 取值）或平台提供的「复制」按钮（点击后从剪贴板读） | 截图 OCR 会把 `B` 读成 `8`、`N` 读成 `W`；记忆会在会话压缩时丢失精度；人工转录更不可靠——这些错误**在功能层面不报错**，数据静默流进错误的账号 | GA4 Measurement ID 从截图里读，`7BB4N5` 变成 `78B4W5`，代码里埋的是错的 ID，GA4 实时报告永远收不到数据但页面不报错 |
| 拿到 ID 后**立刻写进代码或配置**，不要先存到中间变量、临时文件、或对话里隔几轮再用 | 中间步骤越多，被压缩、被覆盖、被手误的概率越高 | 先「记住」ID，做完其他事回头再用，结果用的是压缩后的残值 |
| 部署后用线上 HTML **反向 grep** 确认 ID 与控制台里的一致 | 唯一的闭环验证；光看代码里有没有不够，要看线上跑的是不是对的那个 | 代码里有 ID、部署成功、但 ID 是错的——三个绿灯全亮，数据全丢 |

## 二十、省 token 工作流

1. **上线/改版验收优先命令化**：优先 `node scripts/verify-live.mjs <url...>`，只读 PASS/FAIL 简表，不让主线程自己 curl/grep。
2. **阶段收尾及时换乘**：阶段收尾时建议主线程开新会话，靠项目 `.rankup/` 接续。
3. **排查与重活按收益委派**：独立且能完整描述的重活适合委派，以降低主线程上下文成本；串行定位可由主执行者完成。模型路由见本章「模型档位」，派单与收回按「主 Agent 与子 Agent 分工」，主 Agent 核对依据后再采用简报。
4. **后台任务善用自动通知**：后台任务完成会自动通知，不要轮询进度；子 agent 用 Monitor 等待时写明退出条件和超时。

## 二十一、禁止建设中内容与功能区域

**规则：rankup 任何环节产出的站点、页面、设计稿、样张与功能，都不得出现「建设中」类文案或未实现的功能区域。** 半成品观感会伤害用户信任与质量判断；把未完成能力摆出来也会让用户误以为已经可用。

- **文案范围**：正文、按钮、卡片、空状态、title、description、OG、alt、aria-label、JSON-LD、错误页、sitemap/feed 文字、llms.txt 等任何用户可见处均适用。禁止 coming soon、under construction、work in progress、WIP、TBD、TODO、stay tuned、check back、launching soon、not yet available、will be added/available、in development、待定、建设中、敬请期待、即将上线及同义表达；机械词表的唯一数组在 [`no-wip-check.mjs`](../scripts/no-wip-check.mjs)，同义表达仍须人工核对。
- **功能范围**：未实现的功能不展示入口、不留区块；禁止点了无响应或只弹待上线提示的按钮、没有后端的提交表单、无数据的期待卡片、占位 Pricing/Newsletter/Login 入口及空壳标签页。缺数据就省略该行或整个区块，不写占位话术。
- **设计范围**：设计稿、样张与设计说明同样适用；不能设计待上线状态的卡片或入口，也不能规定这类文案。页面与功能范围只纳入本版本能完整实现的能力。
- **判据**：渲染内容与附属公开文件词表命中为零；逐入口实际操作有实现与结果，需要后端的入口有真实闭环；设计稿与说明无待上线状态。机器检查不能证明功能闭环或覆盖所有同义表达，须配合逐入口与设计回读；阶段闸门只见 [`checklists.md`](checklists.md) 段 3、4、7。
- **例外**：表单控件的 `placeholder` 属性是输入提示，不算此类文案；代码里的 TODO 注释不属于用户可见文案，但不得渗入页面。代码标识符与 CSS 类名不是用户文案，不按裸源码词表命中判失败。

## 二十二、部署红线：先合入对应环境分支并推送，再部署

- **规则**：要部署哪个环境，就先把改动合并到该环境对应的分支（测试线进测试分支，生产进生产/默认分支）并推送到远端，再由团队现有流水线从该分支构建部署。没合并、没推送就不构建、不部署；禁止用本机未推送提交、功能分支或“叠加到在跑镜像”的方式出镜像。
- **为什么**：别人从分支拉代码发布。改动只在线上不在分支，下一次他人发布就会把它冲掉；反过来，不基于远端最新代码构建，会覆盖他人已上线的改动。【实测】某项目 2026-10-23 用本机未推送代码发布，覆盖了同事已上线修复。
- **线上值守**：发布或任何线上写入开始起，派单方挂一个低成本的值守执行者（模型档位按 `/agent-fleet` 当前路由）每 10 分钟检查服务实例就绪与重启、错误日志、关键接口或页面冒烟和本次变更相关指标；异常立即通知派单方并按项目回滚路径处理。发布后观察结束、服务稳定且异常已处理时结束值守，检查结果、异常与结束时间记入发布报告；具体检查项由项目 AGENTS.md 规定。
- **发布前必核**：`git fetch` 后候选包含该环境远端分支最新头；线上在跑提交是候选的祖先；生产提交在测试分支有等价提交（`git cherry` / patch-id）；本机环境分支与远端同步、无未推送提交。
- **生产线改动再加三步**：测试线通过不等于生产线通过，两条环境线分叉时，搬过去的改动必须在目标线上真实启动并验证，不引用来源线的绿灯；先做预发验证再发生产（预发只验启动与只读冒烟，不写脏共享数据），没有独立预发就在发布报告写明替代办法；发布后自测（登录、核心读写、错误率），失败按流水线回退。团队后端项目更细的构建期检查由项目自己的规则文件规定。
- **判据**：发布报告有「分支合规」一节，逐条给上述证据与合并链接、流水线记录；生产线改动另写明预发验证与发布后自测的命令、读回结果与时间；缺任一项按未完成处理，先补合并推送再继续放量。项目可在自身规则文件写更细的分支映射、预发入口与检查命令。
