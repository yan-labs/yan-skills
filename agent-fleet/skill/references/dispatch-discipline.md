# 派单纪律

## Brief

围绕一个目标写 brief。CLI 生成归类、REPORT 和[六条思维准则](../templates/blocks/thinking-principles.md)。路径、环境和证据先核实。项目内长期固定的约定放进项目场景，本单正文补变化项。放行行为见[派单检查](fleet-go.md#派单检查)。

| 要核实的事 | 写法 |
|---|---|
| 仓库与文件 | 写真实仓库、基点、读写范围和关键文件绝对路径。新文件核对父目录，并行写入分配独立工作树或安排先后 |
| 真实环境身份 | 写目标环境、入口、账号或权限、版本和所需夹具。测试、预览和生产回读各绑定实际对象 |
| 证据在哪取 | 写命令、产物或回读入口及通过判据。授权外动作明确 owner |
| 备用验收 | 主入口不可用时指定可核查的等价路径和可接受偏差。只能交近似结果时写清缺口 |

在「验收」下每项单独编号，格式用 `V1 目标及取证入口｜owner：本单`。派单方或外部渠道供数时写 `外部:责任方`，下游写 `下游:任务名`。共享证据由 owner 获取一次再分发。跨服务发布按阶段写各自验收。给出交付清单和停止条件。

依任务选有区分力的验收。缓存覆盖所有写入路径和回填竞争。灰度检查关闭语义、旧数据隔离、真实并发分母、槽位释放和优先级竞争。幂等重领覆盖读检查点失败、写前写后故障及新旧通道。数据替换先证实新数据落地再删旧，归档重跑时重新核副本。重连验证瞬时失败后的有界恢复。设备实测核可用视口、实际输入通道和备用证据。

## 角色与样板

1. 普通执行者负责做到验收结束，在当前线程执行。明确授权的总管才可拆下游并汇总各 owner 的交付。
2. 复核者自己写本单 REPORT。项目文件只读，临时文件放隔离目录。
3. 本单触发的外部条件用 park。派单方供给的验收项标「等外部」交回。
4. 换班条件优先于普通完成条件。写权威快照再结束，`pending=handoff` 交接下一棒。
5. 发布建议写回滚条件。已注入发布授权且正文缺条件时使用发布前版本或开关 0% 的默认回滚，报告记「已回滚」并附回读。

代码按模型和角色选择样板。Terra 聚焦指定入口和验收，Sol 聚焦根因与可验证备用路径，Astra 用反例约束复杂方案。复核和总管用对应的角色规则。按预览核对授权、已知坑和停止条件。

## 报告与独立复核

逐项核对报告「结论」、实际产物、提交和回读。只读复核给代码、差异和验收边界，避免预先给 maker 的结论。独立复核的风险分档按全局规则执行。每个必修项标明现实会发生或仅极端条件，以及能否靠 brief 预防。后续复核围绕新差异和仍会出现的问题。账本尾注见[复核尾注](ledger.md#复核尾注)。

## 派单复盘

启动被拦、未达验收或复核发现必修项时，先按证据归因：入口与环境、范围与授权、场景与样板、实现与验收，或执行通道本身。只有能预防复发的原因才按[记忆规范](memory.md)更新规则；机械契约优先交给代码或场景。连续在同一位置返工时重新验证设计与根因。

代码考古看历史和关键合入以判断约束是否仍存在。交接成本审查看新人需要补的上下文。性能回顾区分流水线耗时与合入后的退化。返工复盘找共因和可证伪的预防办法。

## 总管与时间关键步骤

总管接整条链路，记录阶段、依赖、授权、所有者与放行判据。执行窗口用独立的触发机制或 runner 条件，避免会话闲置时的定时器成为唯一触发。并发生产变更按项目计划错开，保留可归因的回读。失败时先核旧进程、真实状态和已授权的恢复动作，再决定重派。

## /design 画布

由适合的执行者在本地交付画布文件，需应用内上传时交给具备对应工具的角色串行操作。验证最终产物入口。
